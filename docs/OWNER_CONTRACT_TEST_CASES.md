### Когда переходить к кейсам

Кейсы K/N и регрессии ниже относятся к детерминированной проверке контрактов из данных. Для их начала нужны свежий UI Apollo, доступный Proxy и перечисленные подключённые ревизии в колонке «Проверка». Само исправление скачивания обновлений приложения этими кейсами не проверяется.

Подтверждённая версия Proxy позволяет переходить к этим кейсам после проверки свежего UI и подключённых ревизий. Ждать сборку 2026102902 не нужно. Успешное обновление приложения и данных само по себе не подтверждает приёмку Figma-кейсов. Сетевую ошибку или проблему запуска фиксируй отдельно от нарушения правила компонента.

## 2. Как выполнять каждый кейс

1. Открой ссылку в таблице и выдели **сам экземпляр компонента**, а не карточку с подписью или общий фрейм. Для Segment ссылки выбирают вложенный экземпляр. Если ссылка только приблизила холст, выбери указанный компонент в слоях.
2. В Apollo открой **«Дизайн»**, выбери **Desktop** в шапке и канал **b2b** в настройках. MobileWeb указан отдельно там, где нужен. Для этих локальных правил специальный «Тип страницы» не требуется.
3. Если раньше загружал ZIP вручную, открой **«Источники проверки» → «Использовать прокси»**. Это возвращает проверку к доставленным контрактам.
4. Нажми **«Проверить»** и дождись результата. После изменения параметра нажимай её заново: предыдущий результат относится к прежнему состоянию.
5. Смотри **«Компоненты» → «Кастомы»**. «База», «Стили и токены» и «Пора обновить» имеют свои проверки. Их замечания фиксируй отдельно; общий счётчик не равен числу нарушений одного контракта.
6. После обязательного шага открой **«Источники проверки» → «Полная диагностика»** и сохрани `apollo-v4-….json`. Кнопка **«Сохранить сводку»** полезна для краткого итога, но для разбора UNKNOWN и вложенных частей нужен полный отчёт. AI-объяснение для этих тестов не требуется.

Подготовленные отрицательные кейсы уже содержат мутацию. Дополнительные эксперименты с оформлением делай на копии экземпляра. Автоисправление может убрать тестовую мутацию — сначала сохрани результат.

## 6. Как трактовать неполноту и известные границы

- **UNKNOWN / «Нужна проверка» / «Нет подтверждённых данных»** — правило не получило достаточных фактов. Это не подтверждённое нарушение нормы и не успешная приёмка. Нужны контекст и полный JSON.
- **Подтверждённо выключенный элемент** может давать «неприменимо». Например, Label=False у соответствующего Segment и Pips=False у Slider. «Не удалось прочитать элемент» не равно «элемент выключен».
- **Slider r3 и Segment r1 уже подключены к доставке.** Записи «ещё не опубликован», «нужен контракт Segment» и «Slider: проверить только 4 варианта» в старых отчётах описывают прежний этап. Для этой приёмки используются текущие версии из раздела 1.
- **SelectWithTags:** внутренние private Tag/TagControl не приравнены к публичному Tag. Видимость ErrorMessage проверяется, проверка непустого текста сообщения не заявлена. Предыдущий широкий обход источника завершался read-only отказом; полное свежее чтение всех вложенных целей ещё должно подтвердиться в Apollo.
- **SliderInput:** его private Slider имеет другую библиотечную идентичность. Наличие контракта публичного Slider r3 не означает автоматического покрытия всех самостоятельных норм private Slider.
- **OptionsList:** в текущем API нет обещанного старой документацией Boolean Scrollbar. Этот конфликт сохранён отдельно; переключатель для теста придумывать не нужно. Текстовые проверки не должны требовать текст у действительно пустых служебных частей.
- Выбор компонента в продуктовом контексте, смысл подписи, интерактивность, клавиатура и поведение фронта не принимаются этим статичным прогоном. Контракт остаётся Draft по фактическим открытым областям; один зелёный экран не повышает его автоматически до Ready.
