## Section 1: Определение

`FilterBar` — панель управления выдачей перед таблицей, списком или другой группой данных. Через неё пользователь ищет, применяет фильтры и настраивает состав быстрого доступа.

`FilterBar` заменяет `FiltersBlock` на Desktop и Mobile Web.

Этот pattern описывает применение компонента на продуктовом экране: расположение, тексты, состояния выдачи, сохранение конфигурации и межкомпонентный flow. Exact constraints самого компонента хранятся в `component:web-corp.filter-bar.*`.

## Section 2: Когда использовать

Используйте `FilterBar`, когда пользователю нужно:

- искать внутри конкретной таблицы, списка или реестра;
- применять один или несколько фильтров;
- видеть активные условия рядом с управляемой выдачей;
- добавлять второстепенные фильтры в быстрый ряд;
- настраивать видимость и порядок фильтров;
- выбирать готовый или произвольный период;
- возвращаться к настроенной ранее компоновке;
- понимать причину пустой выдачи после фильтрации.

Используйте Mobile Web-представление при ширине `320–767 px`, а Desktop — от `768 px`.

## Section 3: Когда не использовать

Не используйте `FilterBar`, если:

- поиск относится ко всему разделу, а не к расположенной рядом группе данных;
- для сценария достаточно одного локального контрола;
- на экране нет выдачи, которой управляют поиск и фильтры;
- продукт не может обеспечить синхронизацию значений между быстрыми и расширенными мобильными фильтрами;
- произвольный контрол пытаются замаскировать под существующий пресет.

Если нужную фильтрацию невозможно реализовать поддерживаемыми пресетами, запросите новый тип у дизайн-системы.

## Section 4: Принципы

1. Располагайте FilterBar рядом с выдачей, которой он управляет.
2. Рассматривайте FilterBar и выдачу как одну функциональную область.
3. Сохраняйте пользовательскую компоновку, но не переносите значения и поисковый запрос в следующую сессию.
4. Показывайте активные условия: фильтр со значением нельзя скрывать.
5. По умолчанию показывайте все основные фильтры; второстепенные можно вынести в `Ещё`.
6. Не вводите количественный лимит фильтров только из-за демонстрационного макета.
7. Разделяйте недоступную опцию одного фильтра и продуктовую зависимость между фильтрами.
8. Применяйте составной мобильный выбор только после явного подтверждения.
9. Сохраняйте выбранные значения при переходе между Desktop и Mobile Web.
10. Разделяйте ответственность: компонент управляет контролами и callbacks, продукт — данными, хранением, loading, error, empty state, зависимостями и метриками.

Порядок Search, платформенные контролы, допустимые пресеты, reset semantics, View и внутренний порядок Date определяются component rules и не дублируются в этом pattern.

## Section 5: Структура текста

### Search

Плейсхолдер должен подсказывать, что можно ввести. Не повторяйте слово `Поиск`, если оно не добавляет смысла.

Во время ввода Search не показывает варианты автокомплита. При пустом фокусе можно показывать `Недавно искали`.

Enter применяет запрос и передаёт его продукту для записи в историю.

### Названия фильтров

Называйте категорию существительным в единственном числе:

```text
Компания
Карта
Тип операции
Счёт
```

Если выбрано несколько значений, добавляйте количество после названия в единственном числе:

```text
Счёт (3)
```

### Период

Если значение не выбрано заранее, используйте:

```text
Период
```

Сокращения месяцев, дней и дат оформляйте по редакционному гайду интерфейсных текстов.

### Сброс

Каноническое название:

```text
Сбросить
```

Не используйте `Сбросить всё`: действие очищает значения и Search, но не пользовательскую компоновку.

### Пустая выдача

Сообщение должно:

- объяснить, что по заданным условиям ничего не найдено;
- предложить изменить условия;
- предложить сбросить часть фильтров.

### Настройка

Для боковой панели подходит инструкция:

```text
Управляйте видимостью и порядком фильтров на странице
```

## Section 6: Правила

### Rule 1: Размещайте FilterBar рядом с выдачей

- ruleId: rule:components.filter-bar.near-filtered-content
- severity: error
- appliesTo: screen
- checkType: llm
- autofix: no

FilterBar должен находиться непосредственно перед таблицей, списком или другой группой данных, которой он управляет.

#### Правильно

```text
FilterBar → таблица платежей
```

#### Неправильно

```text
FilterBar в общей шапке → несколько блоков → таблица
```

#### Почему

Положение объясняет область действия поиска и фильтров.

### Rule 2: Соблюдайте отступ от TabsView

- ruleId: rule:components.filter-bar.desktop-tabs-spacing
- severity: error
- appliesTo: screen
- checkType: deterministic
- autofix: no

На Desktop отступ между `TabsView` и `FilterBar` равен `24 px`.

#### Правильно

```text
TabsView → 24 px → FilterBar
```

#### Неправильно

```text
TabsView → 16 px → FilterBar
```

#### Почему

Фиксированный отступ поддерживает ритм заголовочной области.

### Rule 3: Соблюдайте отступ от TitleView

- ruleId: rule:components.filter-bar.desktop-title-spacing
- severity: error
- appliesTo: screen
- checkType: deterministic
- autofix: no

На Desktop отступ между `TitleView` и `FilterBar` равен `32 px`.

#### Правильно

```text
TitleView → 32 px → FilterBar
```

#### Неправильно

```text
TitleView → 24 px → FilterBar
```

#### Почему

Отступ отделяет заголовок от управления выдачей.

### Rule 4: Примыкайте FilterBar к Table с topbar

- ruleId: rule:components.filter-bar.table-adjacency
- severity: error
- appliesTo: screen
- checkType: deterministic
- autofix: no

Между `FilterBar` и `Table` с `topbar` нет дополнительного отступа.

#### Правильно

```text
FilterBar → 0 px → Table с topbar
```

#### Неправильно

```text
FilterBar → 24 px → Table с topbar
```

#### Почему

Бар и таблица образуют одну функциональную область.

### Rule 5: Отделяйте FilterBar от другого контента

- ruleId: rule:components.filter-bar.desktop-content-spacing
- severity: recommendation
- appliesTo: screen
- checkType: deterministic
- autofix: no

Если после FilterBar находится не `Table` с `topbar`, рекомендуется отступ `24 px`. Продукт может изменить его под контекст.

#### Правильно

```text
FilterBar → 24 px → список карточек
```

#### Неправильно

```text
Для любого контента принудительно используется 0 px
```

#### Почему

Другие группы контента обычно требуют визуального разделения.

### Rule 6: Соблюдайте мобильный отступ от хедера

- ruleId: rule:components.filter-bar.mobile-header-spacing
- severity: error
- appliesTo: screen
- checkType: deterministic
- autofix: no

На Mobile Web FilterBar находится сразу под хедером с отступом `12 px`.

#### Правильно

```text
Header → 12 px → FilterBarMobile
```

#### Неправильно

```text
Header → 24 px → FilterBarMobile
```

#### Почему

Бар остаётся доступным в начале мобильного экрана.

### Rule 7: Сохраняйте только пользовательскую конфигурацию

- ruleId: rule:components.filter-bar.persist-configuration
- severity: error
- appliesTo: flow
- checkType: manual
- autofix: no

Продукт сохраняет видимость, порядок и добавленные фильтры в разрезе `пользователь + экран`. Значения и поисковый запрос между сессиями не сохраняются.

Компонент передаёт изменения через callback. Если базовый набор изменился, объедините его с сохранённой конфигурацией: удалите отсутствующие фильтры, добавьте новые и по возможности сохраните пользовательские видимость и порядок.

#### Правильно

```text
Новая сессия → прежняя компоновка → пустые значения и Search
```

#### Неправильно

```text
Новая сессия → прежние значения автоматически влияют на выдачу
```

#### Почему

Компоновка экономит повторную настройку, а старые условия не должны неожиданно менять новую сессию.

### Rule 8: Давайте очистить историю Search

- ruleId: rule:components.filter-bar.search-history
- severity: error
- appliesTo: flow
- checkType: manual
- autofix: no

Продукт предоставляет и хранит историю через callback. При пустом фокусе рекомендуется показывать до трёх последних запросов, но продукт может увеличить количество.

Историю обязательно можно очистить.

#### Правильно

```text
Пустой фокус → Недавно искали → Очистить
```

#### Неправильно

```text
История показывается без возможности очистки
```

#### Почему

Поисковые запросы могут содержать чувствительные данные.

### Rule 9: Называйте фильтры в единственном числе

- ruleId: rule:components.filter-bar.singular-filter-label
- severity: warning
- appliesTo: text
- checkType: llm
- autofix: partial

Название категории фильтра должно быть существительным в единственном числе.

#### Правильно

```text
Компания
Счёт
Карта
```

#### Неправильно

```text
Компании
Счета
Карты
```

#### Почему

Единая форма делает подписи компактными и согласованными.

### Rule 10: Показывайте количество выбранных значений

- ruleId: rule:components.filter-bar.multiselect-count
- severity: error
- appliesTo: text
- checkType: deterministic
- autofix: partial

Если выбрано больше одного значения, добавляйте количество в круглых скобках после названия в единственном числе.

#### Правильно

```text
Счёт (3)
```

#### Неправильно

```text
Счета: 3
```

#### Почему

Формат сохраняет узнаваемое название фильтра и показывает объём выбора.

### Rule 11: Показывайте пустое состояние после фильтрации

- ruleId: rule:components.filter-bar.filtered-empty-state
- severity: error
- appliesTo: screen
- checkType: llm
- autofix: partial

Если условия заданы, но результатов нет, покажите причину и предложите изменить или сбросить фильтры.

#### Правильно

```text
Ничего не нашли по заданным условиям. Измените или сбросьте фильтры.
```

#### Неправильно

```text
Пусто
```

#### Почему

Пользователь должен понимать причину и следующий шаг.

### Rule 12: Оставляйте loading, error и empty state продукту

- ruleId: rule:components.filter-bar.product-owned-loading
- severity: recommendation
- appliesTo: screen
- checkType: manual
- autofix: no

FilterBar статичен. Общей загрузкой, ошибкой и пустой выдачей управляет продуктовый экран.

Локальная загрузка допустима внутри отдельного фильтра, если его значения получаются асинхронно.

#### Правильно

```text
Асинхронные значения одного фильтра → локальная загрузка внутри списка
```

#### Неправильно

```text
FilterBar самостоятельно управляет загрузкой таблицы
```

#### Почему

Компонент управляет контролами, но не жизненным циклом продуктовых данных.

### Rule 13: Подключайте стандартные метрики

- ruleId: rule:components.filter-bar.alfametrics
- severity: warning
- appliesTo: flow
- checkType: manual
- autofix: no

Продукт подключает стандартный `alfametrics`. Отдельный обязательный список событий в FilterBar pattern не задаётся.

#### Правильно

```text
FilterBar подключён к стандартному alfametrics
```

#### Неправильно

```text
Команда придумывает несовместимую схему метрик только для одного экрана
```

#### Почему

Стандартный механизм сохраняет сопоставимость аналитики между продуктами.

### Rule 14: Определяйте поведение взаимосвязанных фильтров в продукте

- ruleId: rule:components.filter-bar.dependent-filters
- severity: recommendation
- appliesTo: flow
- checkType: manual
- autofix: no

Опция, существующая, но недоступная в контексте одного фильтра, может оставаться видимой и заблокированной.

Для взаимосвязанных фильтров продукт решает, скрывать ли значения, блокировать их или очищать после изменения другого фильтра.

#### Правильно

```text
Недоступная по роли опция → видима и disabled
Зависимость двух фильтров → поведение определил продукт
```

#### Неправильно

```text
Правило disabled-опции автоматически применено ко всем зависимым фильтрам
```

#### Почему

Это разные сценарии, и универсальное поведение может нарушить продуктовую логику.

### Rule 15: Показывайте основные фильтры по умолчанию

- ruleId: rule:components.filter-bar.show-filters-by-default
- severity: recommendation
- appliesTo: screen
- checkType: manual
- autofix: no

Количественного лимита нет. По умолчанию рекомендуется показывать все основные фильтры; второстепенные команда может вынести в `Ещё`.

#### Правильно

```text
Основные фильтры видимы → второстепенные доступны через Ещё
```

#### Неправильно

```text
Показано ровно пять фильтров только из-за Figma-примера
```

#### Почему

Состав определяется задачей экрана, а не техническим устройством макета.

### Rule 16: Сохраняйте значения при смене платформенного вида

- ruleId: rule:components.filter-bar.preserve-responsive-values
- severity: error
- appliesTo: flow
- checkType: manual
- autofix: no

При переходе между Desktop и Mobile Web выбранные значения сохраняются.

#### Правильно

```text
767 px → 768 px → значения сохранены
```

#### Неправильно

```text
Смена ширины → выбранные фильтры сброшены
```

#### Почему

Адаптивная перестройка не должна прерывать пользовательский сценарий.

### Rule 17: Применяйте мобильный выбор по его типу

- ruleId: rule:components.filter-bar.mobile-apply-flow
- severity: error
- appliesTo: flow
- checkType: manual
- autofix: no

Одиночный мобильный выбор применяется сразу. Множественный выбор и произвольный период применяются кнопкой `Применить`.

Если пользователь закрывает составной выбор без применения, неподтверждённые изменения отменяются.

#### Правильно

```text
Один вариант → применён сразу
Несколько вариантов → Применить
Другой период → Применить
```

#### Неправильно

```text
Множественный выбор → закрытие без применения → выдача изменилась
```

#### Почему

Пользователь должен явно завершить составной выбор.

## Section 8: Примеры

### Desktop с Table

```text
TitleView
32 px
FilterBar
0 px
Table с topbar
```

FilterBar и таблица образуют одну область. Действие `Сбросить` очищает значения и Search, но сохраняет пользовательскую компоновку.

### Desktop после TabsView

```text
TabsView
24 px
FilterBar
24 px
Список карточек
```

Для контента без `Table topbar` используется рекомендуемый отступ `24 px`.

### Mobile Web

```text
Header
12 px
FilterBarMobile
  Search
  Быстрые фильтры
  Все фильтры
```

Значения в `Все фильтры` синхронизированы с быстрым рядом. Представление определяет продукт; состав и порядок FilterBar там не изменяются.

### Responsive

```text
767 px → FilterBarMobile
768 px → FilterBarDesktop
```

При смене представления выбранные значения сохраняются.

### Пустая выдача

```text
Ничего не нашли по заданным условиям. Измените или сбросьте фильтры.
```

## Section 9: Антипримеры

### FilterBar далеко от выдачи

```text
FilterBar в шапке
...
несколько несвязанных блоков
...
таблица
```

Пользователь не понимает область действия условий.

### Значения сохраняются между сессиями

```text
Новая сессия → автоматически применены прошлые фильтры
```

Сохраняется компоновка, но не значения и Search.

### Сброс уничтожает компоновку

```text
Сбросить → очищены значения, порядок и видимость
```

Действие должно очистить только значения и Search.

### История без очистки

```text
Недавно искали → нет действия очистки
```

История может содержать чувствительные данные.

### Жёсткий лимит по Figma-примеру

```text
Разрешено не больше пяти фильтров
```

У FilterBar нет количественного ограничения.

### Неподтверждённый мобильный выбор

```text
Множественный выбор → закрытие → значения применены
```

Закрытие без `Применить` должно отменить изменения.

## Section 10: Машинная обработка

### Детерминированные проверки

Можно автоматически проверять:

- отступы `24 px`, `32 px`, `0 px` и `12 px` в известных композициях;
- формат `{Название} ({N})`;
- текст действия `Сбросить`;
- отсутствие текста `Сбросить всё`;
- границу Desktop от `768 px`;
- наличие действия очистки рядом с историей;
- компонентный состав после появления generated composition contract.

### Словарные проверки

Можно проверять:

- названия фильтров по словарю единственного числа;
- `Период` при отсутствии предвыбранного значения;
- канонические названия `Недавно искали`, `Применить`, `Сбросить`;
- запрещённую формулировку `Сбросить всё`.

### LLM-проверки

С помощью LLM можно проверять:

- связь FilterBar с расположенной рядом выдачей;
- полезность плейсхолдера Search;
- полноту пустого состояния;
- оправданность вынесения фильтров в `Ещё`;
- различие недоступной опции и продуктовой зависимости;
- корректность границы ответственности компонента и продукта.

### Не проверяется автоматически

Требует продуктовой или ручной проверки:

- хранение конфигурации в разрезе `пользователь + экран`;
- объединение новой базовой конфигурации с сохранённой;
- сохранение значений при адаптивном переключении;
- применение и отмена мобильного составного выбора;
- синхронизация быстрых и расширенных мобильных фильтров;
- поведение взаимосвязанных фильтров;
- локальная загрузка асинхронных значений;
- подключение `alfametrics`;
- выбранное продуктом представление в `Все фильтры`.

### Автоисправления

Допустимы безопасные автоисправления:

- привести счётчик к формату `{Название} ({N})`;
- заменить подтверждённую словарём форму множественного числа на единственное;
- заменить `Сбросить всё` на `Сбросить`;
- заменить пустое название Date на `Период`.

Не исправляйте автоматически:

- состав, порядок и видимость фильтров;
- тип пресета;
- сохранённую пользовательскую конфигурацию;
- mobile apply flow;
- поведение зависимых фильтров;
- представление `Все фильтры`;
- метрики.
