Рабочий черновик для обсуждения. Новые нормативные правила и исполняемые проверки не добавлены. Упомянутые нормы сохраняют существующих владельцев и RuleID; этот файл не подключён к каталогу Apollo.

## 1. Задача паттерна

Помочь выбрать композицию контентной области продуктовой страницы: какие зоны нужны, какую ширину они занимают и как связаны с сеткой. Начальный фокус — формы и просмотровые страницы Альфа-Бизнеса на desktop.

«Просмотровая страница» здесь означает страницу с просмотровой формой или реквизитами. Автоматически распространять схему на любую страницу просмотра, например таблицу, нельзя.

Канал AB задан отдельно от платформы: изменение ширины экрана не переводит интерфейс в ABM. Адаптивную версию этого черновика ещё предстоит уточнить.

## 3. Рецепт применения

1. Определить тип страницы и основную задачу пользователя.
2. Определить, нужен ли самостоятельный дополнительный контент — островок. Наличие свободного места само по себе не обосновывает его добавление.
3. Выбрать композицию по действующим источникам и проверить условия её применения.
4. Собрать зоны на сетке через переменные нужного режима. Сохранить предусмотренные компонентами привязки и наследование.
5. Проверить фактическую ширину зон, расстояние между ними и поведение на нужных ширинах экрана.

| Контекст | Композиция из существующих источников | Основание |
| --- | --- | --- |
| Форма или просмотровая форма с островком на широком desktop; подтверждённые примеры — 1600 и 1440 px | Основная зона 8 колонок + островок 4 колонки | `rule:layout.wide-grid.use-8-plus-4` |
| Форма без островка на широком desktop | Основная зона сохраняет 8 колонок; островок не добавляется ради схемы | `rule:layout.wide-grid.keep-8-cols-without-island` |
| Главная, табличный раздел, табличная карточка, лендинг внутри страницы | Широкий основной контент занимает 12 колонок | `rule:layout.wide-grid.use-12-columns` |

Третья строка показывает границу применения 8+4; подробные рецепты этих типов страниц пока не входят в черновик. Ширина просмотровой страницы без островка требует отдельного подтверждения: правило для формы без островка не обобщаем автоматически.

## 4. Два исходных требования и их проверяемая часть

### Выбор композиции 8+4

Исходная формулировка: «Для форм и просмотровых страниц на desktop используется 8/4».

Уточнение для обсуждения: «Для страницы формы или просмотровой формы с островком на широком desktop основная зона занимает 8 колонок, дополнительная — 4». Граница перестроения пока не согласована; см. вопросы ниже.

Основание: [Широкая сетка, Rule 7](p_wide-grid.md#rule-7-используй-84-для-форм-и-просмотровых-страниц-с-островком), `rule:layout.wide-grid.use-8-plus-4`.

Проверяемые факты: тип страницы, наличие островка, ширина viewport, границы основной и дополнительной зон, эффективные значения соответствующих колонок. Определение назначения зон относится к контексту; сравнение их размеров с сеткой можно автоматизировать при наличии этих фактов.

8+4 обозначает колонки с учётом межколоночных расстояний. Проверка простого отношения ширин в пикселях 2:1 недостаточна. Число непосредственных дочерних слоёв само по себе также не доказывает композицию.

### Связь layout с Grid & Cols

Исходная формулировка: «Для назначения сетки используются переменные из коллекции [D] Grid & Cols».

Уточнение для обсуждения: «На desktop layout страницы использует переменные [D] Grid & Cols в подходящем режиме; ширины колоночных зон и горизонтальный промежуток между ними связаны с переменными колонок и Gutter».

Основания: `rule:layout.wide-grid.variable-set-by-platform`, `rule:layout.wide-grid.desktop-variable-modes`, `rule:layout.wide-grid.use-width-variables-and-gutter`; для композиции Content/Isle — `rule:components.corporate-page.section-column-widths-variable-only` и `rule:components.corporate-page.section-gutter-required` в [CorporatePage](p_corporate-page.md).

Проверяемые факты: идентичность коллекции и переменных, действующий режим с учётом наследования, привязки соответствующих свойств, итоговая геометрия. Отдельное назначение режима на каждом дочернем слое не подразумевается. Применение переменных не следует смешивать с ручной заменой защищённого grid style корня CorporateContent. Требование Gutter между зонами не задаёт универсальный вертикальный отступ для всего Body.

| Источник evidence | Что позволяет проверить |
| --- | --- |
| Снимок интерфейса | Видимое расположение и приблизительное соотношение зон; привязки к переменным не подтверждает |
| Figma через плагин/MCP с доступными нужными свойствами | Границы зон, привязки, разрешённые значения переменных и действующий режим; контекст страницы нужен отдельно |
| Frontend через DOM и стили | Фактическую геометрию и доступные CSS-привязки; принадлежность к Figma-коллекции требует отдельного сопоставления токенов |

Нет необходимых данных — «не удалось проверить». Противоречие источников — вопрос к норме, а не автоматически нарушение макета. Схема исполняемых проверок для этого черновика пока не определена.

## 5. Что уточнить при грумминге

1. **Граница 1280 px.** В [Широкой сетке](p_wide-grid.md) `rule:layout.wide-grid.stack-8-plus-4-at-1280` требует перестроение при 1280 px и меньше. В [Островках](p_islands.md) `rule:layout.islands.desktop-grid` сохраняет 8+4 при 1280 px и больше, а `rule:layout.islands.adaptive-full-width` переносит островки при 1279 px и меньше. На 1280 px источники расходятся; новое значение здесь не выбираем.
2. **Форма без островка при уменьшении ширины.** Уточнить, до какого диапазона сохраняются 8 колонок и когда основная зона становится полноширинной.
3. **Просмотровая страница без островка.** Подтвердить отдельный вариант и его ширину.
4. **Планшетный диапазон.** Широкая сетка указывает [T] Grid & Cols для 768–1023 px, а CorporatePage, `rule:components.corporate-page.corporate-content-platform-breakpoint`, указывает [D] CorporateContent и режим 768 коллекции [D] Grid & Cols на ширине 768 px. Прежде чем расширять паспорт за пределы desktop, сверить актуальный контракт.
5. **Единый владелец нормы.** Выбрать, остаётся ли новый документ рецептом выбора композиции со ссылками на Широкую сетку или становится владельцем правил композиции. Во втором случае переносить правила с сохранением RuleID и синхронизацией источников; новые копии тех же норм не создавать.

Предложение для первого шага: оставить этот документ рецептом компоновки со ссылками на существующие нормы, разобрать три кейса — форма с островком, форма без островка, просмотровая страница — и уточнить спорные условия на реальных макетах.
