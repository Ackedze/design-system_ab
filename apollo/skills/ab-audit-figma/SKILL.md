# Проверка макета Альфа-Бизнеса

Результат — нарушения с доказательствами и явные границы проверки. Нормы бери
из DS AI HUB; в этом навыке хранится процедура. Запрос проверки разрешает чтение
макета. Правки выполняются только по отдельному поручению.

## Вход и источники

Из ссылки извлеки fileKey и nodeId. Установи продукт, платформу и границу корня;
при необходимости прочитай ближайшего родителя для контекста в пределах
разрешений транспорта (в Apollo — только `snapshot.contextParents`). Не расширяй
аудит на соседние экраны. Предыдущий отчёт и обратная связь — контрольные
наблюдения, не актуальный native snapshot и не источник норм.

Найди доступный DS AI HUB в workspace или в предоставленном пакете. Прочитай его
AGENTS.md, паспорт AB и релевантный маршрут продукта. Registry используй как
индекс, затем читай только файлы обнаруженных компонентов и паттернов.
Статусы draft/verified/deprecated и конфликты источников сохраняй явно.
Длинные документы читай нужными секциями с бюджетом вывода. Обрезанный
фрагмент перечитай адресно до его применения; запись пути в списке источников
не означает, что всё содержимое файла было прочитано.
Не подменяй правила Hub контрактными пакетами Apollo или кодом checker.
Если Hub ссылается на отсутствующие знания, отметь гэп, а не восстанавливай норму
по памяти. Пользовательские исключения действуют в согласованной границе.

В Apollo + Proxy следуй [адаптеру проверки](references/proxy.md): фиксированные native-операции чтения, DS AI HUB из установленного пакета, usage CLI по фазам. Произвольный MCP JavaScript этому исполнителю недоступен.

Для прямой read-only проверки используй MCP и `figma-use` с его session/page/output правилами. Генератор экранов не загружай. При отказе сохрани частичный отчёт и причину; старый snapshot не является текущим.

## Статусы и роль компонентов

Дополнительно используй индексы `JSONS/indexes/lifecycle/deprecated.index.json`,
`scheduled.index.json` и `parts.index.json` из того же закреплённого пакета.
Это метаданные статуса/роли, отдельные от норм DS AI HUB. Сопоставляй точные
опубликованные main/set/variant keys; имя слоя не является ключом.
`deprecated` показывай как ошибку устаревшего компонента, `scheduled` — как
предупреждение о статусе без придуманной даты удаления или общего запрета.
`parts` — ошибка только при подтверждённом самостоятельном использовании:
между экземпляром и страницей нет родительского INSTANCE или COMPONENT.
Выделенный корень может быть вложен в компонент за пределами области;
граница выделения не доказывает самостоятельность. Недоступная, неполная
или противоречивая identity/вложенность даёт UNKNOWN. Конфликт статуса/роли
не замалчивай; конфликт только имени/библиотеки сам по себе не отменяет
доказанную роль. Сохраняй предупреждения исходного индекса.

В Apollo это отдельный `catalogLifecycle` от host: не дублируй его как
модельные проверки Hub и не меняй предупреждение на нарушение.
Отсутствие ключа (`NOT_LISTED`) означает только отсутствие в трёх индексах,
а не правильность компонента. Покрытие индексных проверок и предупреждения
показывай отдельно от покрытия плана правил. До final verify выводы предварительные.

## Карта области и план покрытия

Сначала сними ограниченную карту видимых узлов: ID, тип, имя, вложенность,
количество; отдельно отметь недоступные или исключённые ветви. Для найденных
семейств адресно прочитай component/set key, варианты и нужные свойства.
Имя слоя и наличие связи с библиотекой сами по себе не доказывают соответствие.
У remote master может отсутствовать parent: set key тогда недоступен;
это ограничение чтения не доказывает локальность или неправильную библиотеку.
FRAME раскладки не объявляй подменой компонента без явного требования Hub.

В Apollo список `documentRouting` формирует host по опубликованным ключам
видимых экземпляров и закреплённым индексам пакета. Навигационный индекс
компонентов не является контрактной нормой. До плана прочитай все обязательные
источники и оставшиеся диапазоны `nextReads`; бюджет начальной передачи
не отменяет обязательных хвостов. Метаданные маршрута не считаются чтением норм.
Условные зависимости в `candidateSources` проверь на применимость, а пробелы
и неоднозначность из `gaps` сохрани в отчёте. Полное чтение выбранных документов
не доказывает полноту правил или правильность их интерпретации.

До вынесения вердиктов составь список применимых файлов и проверок:

1. Определи паттерны композиции и компоненты в слотах корня.
2. Разреши ссылки «определяется паттерном/компонентом» до нужных норм.
   Останови циклы через список посещённых файлов. Доступность варианта в API
   проверяется вместе с ограничениями продукта, платформы и контекста.
3. Перечисли правила выбранных паттернов и явные нормы вне секций Rule.
   Для каждого укажи целевые узлы, условие применимости и нужные native поля.
   Правило без ID ссылай на файл и секцию/строку; не придумывай ID Hub.
4. Сохрани строки покрытия до оценки. Непрочитанный документ, неохваченный
   компонент или недоступное поле остаются видимыми пробелами.

Получив host `overrideCoverage`, оцени каждую nodeId+field по Hub. Другое поле/родитель её не закрывает. raw styledTextSegments связан с typed textSegments только через factField host: это прочитанный набор range-полей, не доказательство всех свойств Figma. Metadata не даёт visual proof или прав чтения. Остатки — NOT_CHECKED/UNKNOWN; контекстные правила сохраняются.

В `component-customizations-v1` плагин даёт технические отличия, Proxy — эталоны Athena из закреплённого пакета AB. Агент решает допустимость по Hub. Различие не равно нарушению, равенство не разрешает сценарий. Для comparison включи target requiredField nodeId+field с nativeEvidenceId и точный source catalogueField на catalogueNodeId с catalogueEvidenceId. Не подменяй native каталогом и не цитируй каталог как норму. Пробелы эталонов и неподдержанные поля сохраняй явно. Не запрашивай native-source вместо пакетного эталона. Применимость варианта в паттерне проверяй также без overrides.

Покрытие считай по явно перечисленному набору «правило × целевой узел/область».
Отдельно перечисли экземпляры без собственной проверки и объясни, какие из
них охвачены правилом родителя. 100% выбранного плана не доказывает полноту
инвентаря или всех применимых норм.
Однородные узлы можно группировать в отчёте, сохраняя их ID и индивидуальные
результаты в данных. Не называй выбранную выборку полным аудитом дизайн-системы.

## Чтение и оценка

Прочитай поля из плана компактными адресными запросами. Независимые чтения
можно объединять. Измеряй размер ответа до возврата; при превышении бюджета
разделяй запрос, не обрезай обязательные данные. Не возвращай полные каталоги,
значения всех modes или свойства каждого вложенного instance без необходимости.

Проверяй нужные норме variants, geometry, paints, bindings, typography, effects и sizing на точных слоях. MIXED/UNAVAILABLE не равны пустому значению: читай ranges либо оставь UNKNOWN. Typed requiredFields/factBindings не взаимозаменяемы; сверяй типы с factFieldDefinitions. INSTANCE использует componentProperties. target — цель/потомки, context — предок. По feedback меняй allowedRoles или добавляй sourceRequirement; fact ID/node/target сохраняются, новых прав чтения нет. Local binding/quote repair ограничен двумя шагами: остальные строки сохраняются предварительно. Цитата должна дословно относиться к sourceId этой строки. Доступность факта не означает PASS, объявленный план не доказывает полноту и верность интерпретации.

Сверяй overrides с независимым источником нужного варианта/состояния, учитывая
swaps, разрешённый content и effective variable modes. Master экрана не заменяет
источник настроенного ребёнка. Отсутствие overrides не доказывает соответствие.
Точечно читай внутренний текст/paint для применимой нормы; внутренние примитивы
не считаются самостоятельно размещёнными компонентами.

Для размеров укажи измеряемые границы: bounds компонента, контейнера или
видимого содержимого. При неоднозначной норме сохрани вопрос и UNKNOWN.
Скриншот дополняет свойства; он не доказывает keys, токены или историю detach.
Интерактивность и другие viewport не выводи из одного статического состояния.
Копирайт проверяй только при соответствующем поручении и гейте редполитики Hub.

Каждая строка покрытия получает один статус:

| Статус | Основание |
|---|---|
| PASS | Применимое требование и все нужные факты прочитаны, условие выполнено |
| FAIL | Прочитанная норма и факты доказывают нарушение |
| UNKNOWN | Проверка выполнена, но вывод неоднозначен или данных недостаточно |
| NOT_CHECKED | Проверка или необходимое чтение не выполнены |
| NOT_APPLICABLE | Условие применимости не выполнено; указаны причина и evidence |

Наличие API/instance не переводит визуальные проверки в PASS. Неизвестный
бизнес-сценарий не переводит условное правило в NOT_APPLICABLE. UNKNOWN и
NOT_CHECKED не являются подтверждёнными нарушениями.

## Отчёт и затраты

Сохраняй результаты вне активного навыка, в отдельной папке прогона:

- Отчёт: Figma URL/корень/платформа, нарушения с nodeId, actual, expected,
  source/ruleId, severity источника и конкретным исправлением. Несколько
  нарушений одного компонента можно объединить для чтения.
- Матрица покрытия: rule/source, target IDs, required fields, evidence,
  status, причина; суммы по статусам, выбранный знаменатель и исключённые
  компоненты/ветви. Доля проверенного = (PASS + FAIL) / применимые строки;
  UNKNOWN и NOT_CHECKED входят в знаменатель, NOT_APPLICABLE исключается.
  Этот процент не измеряет полноту всех знаний Hub.
- Evidence: адресные snapshots/сравнения, скрипты запросов, ошибки инструментов
  и один актуальный скриншот, если он нужен для визуальных находок.
- Источники: полный список реально использованных навыков и файлов с путями,
  версиями/хешами, прочитанными фрагментами; список гэпов и проблем сборщика.

Если транспорт поддерживает выдачу по частям, показывай готовые группы
выводов с пометкой «предварительные». Итог требует полной объявленной
матрицы и проверки актуальности. Остановка не превращает частичный результат
в итоговый отчёт; подробности Apollo — в адаптере.

С начала прогона веди учёт отдельно для Figma, чтения документации и отчёта.
Создание/проверку самого навыка учитывай отдельно от его применения.
Сохраняй запросы и текстовые ответы по категориям, учитывай повторные чтения
и ошибки. Файлы, только найденные в индексе, не называй прочитанными.

Если host даёт реальный usage по вызовам/фазам, используй его с указанной
границей измерения. Не раскладывай общий session total по категориям на глаз,
не складывай cumulative totals и не используй usage guardian/чужого агента.
При отсутствии usage запиши фактический расход как UNAVAILABLE. Дополнительно
можно посчитать сохранённый текст reference-токенизатором: укажи encoding,
версию, границу corpus и исключения (изображения, контекст, кэш, reasoning и
неучтённые сообщения). Называй это объёмом текста, а не расходом модели.
Зафиксируй версию отчёта, на которой выполнен подсчёт, чтобы правки не меняли
знаменатель задним числом.

## Повторная проверка и улучшение

Перед завершением сопоставь находки и матрицу: у FAIL есть норма и evidence,
у непроверенного нет PASS; все обнаруженные публичные семейства перечислены
либо охвачены, либо явно исключены. Сохрани небольшие выводы о том, чего
не хватило и что стоит исправить в процессе или знаниях.

При обратной связи сначала установи причину: пропуск чтения/правила,
ошибочная интерпретация, недостаточные знания или ограничение MCP. Исправляй
процедуру в этом навыке, нормы — в Hub только по поручению. Не вшивай ответы
конкретного макета в инструкции. Известные ошибки используй как регрессионный
контроль; такой прогон не является слепым или независимым тестом качества.
