# Источники и Figma workflow

Сначала прочитай `ds-ai-hub/AGENTS.md`, `README.md`, `products/ab/manifest.json`.
Это маршруты, а не закреплённый снимок библиотеки. Корни репозиториев находи
в текущем workspace; в окружении владельца это `ds-ai-hub` и
`shared/design-system_ab`. Не используй historical checkout вместо текущего.

## От брифа к нужным источникам

| Решение | Начальный маршрут в ds-ai-hub |
|---|---|
| Черновой каркас, сетка и области | `products/ab/patterns/draft-layout.md`, `products/ab/components/corporate-content/` |
| Структура и цель лендинга | `products/ab/patterns/landing-pages.md` |
| Первый экран | `products/ab/components/promo-main-block/` |
| Бенефиты и ёмкость | `products/ab/components/benefits/`, `benefit-card/` |
| Содержательные секции | `benefits-block/`, другие компоненты выбранного паттерна |
| Форма/FAQ/файлы | Сначала допустимость и место по landing-pages, затем компонентные маршруты |
| Фон страницы | CorporateContent и mode `BackgroundPlate Color`; не палитра hero |
| Поверхность отдельного блока | `products/ab/components/background-plate/` и контракт блока |
| Цвета и типографика | `core/common/tokens/`, `core/web/tokens/`, `manifest.sources.figmaTokens/figmaStyles` |
| Иконки | `core/web/assets/assets_glyph-26.json`; инструкции IconView по его маршруту |
| Иллюстрации | `products/ab/patterns/images_format.md`; указанные им каталоги Corp Image Library |

Из компонентной папки нужны `instructions.md`, `adapter.figma.md`, точные
`figma-keys.json` и применимые cookbook-разделы. Code adapter и bridge нужны
только если решение затрагивает код/cross-target, а не для обычной сборки Figma.
Не читай все компоненты. Обязательно читай constraints, applicability и public
boundary именно выбранного семейства. Сверь актуальный опубликованный key/API.

Если хаб направляет в `design-system_ab`, выбирай текущий пакет из
`experiments/current-contract-packages/manifest.json`, проверь ZIP hash и прочитай
нужный `contract.manual.json` внутри ZIP. Сохрани путь ZIP и конкретной извлечённой
копии. При отсутствии пакета используй обозначенный хабом manual/catalog
и пометь fallback. Не считай generated inventory самостоятельным нормативным
разрешением. Конфликт источников фиксируй, а не разрешай молча.

Различай прямое противоречие и более узкое совместимое условие. Если выбранная
конфигурация удовлетворяет обоим источникам, сохрани их расхождение и продолжай
в этой общей области. Например, отсутствие нормы про конкретный размер не
равнозначно запрету этого размера. Не блокируй всю страницу из-за конфликта
настройки, которая в этой композиции не используется. Реальное противоречие
выбранной конфигурации остаётся вопросом, а не разрешением обойти контракт.

## До записи

- Получи Figma target; если файла нет — используй штатное создание с выбором
  команды по правилам инструмента. Создай session и переиспользуй её в follow-up.
- Прочитай target страницу без мутаций; сохрани baseline чужих roots.
- Подготовь для выбранных секций keys, публичные свойства, токены/styles,
  fonts, источник ассетов и проверяемые нормы. Тип/роль подтверждай mapping,
  не одним названием слоя. Definitions варианта читай у owning component set.
- Сегмент и viewport определяются запросом/ответами и допустимым профилем,
  а не темой туров, произвольной палитрой или жёстким default из навыка.

## Обязательный каркас отдельной страницы

Сначала создай один CorporateContent и проверь, что всё содержимое страницы
попадает в его Body, SwapMe удалён, root сохраняет Fill/Hug и штатные bindings.
Grid & Cols mode задаётся на внешнем корне; вложенные системные узлы его
наследуют. Колонки, Content и Gutter бери из переменных; не путай ширину
viewport с шириной контентной области. Для Content/Isle используй Section
по его контракту; простая вертикальная композиция может оставаться в Body.

Фон CorporateContent определяется разрешённым page mode, по умолчанию grey.
Внешний каркас прозрачен. `promo-classic` и `Appearance=Dark` главного блока
не задают цвет всей страницы. Host, containment, grid и page background
проверяются до детализации; отсутствие CorporateContent не является
допустимой экономией чернового прогона.

## Во время сборки

Один owned root, Auto Layout для связанного содержимого. Импортированные
instances сохраняются; компонентная геометрия и типографика не переписываются
ради размещения текста. Ширину и context modes задавай контрактным способом.
После swap/variant/slot операции снова находи потомков от стабильного root ID.
Внутренние/imported IDs между MCP-вызовами не переиспользуются.

Для изображений предпочитай разрешённый swap компонента. Если нужен asset
transfer, используй существующий library source image → поддержанный export/
download/upload. Cross-file imageHash без проверки blob и рендера недостаточен.
Не оставляй редакционную Grid, default asset или пустую картинку вместо результата.
Различай три уровня: Fill/Hug/Fixed узла, constraints Scale/Center внутри
родителя и scaleMode Fit/Fill/Crop растровой заливки. Scale у Image не делает
его внешний ImageView резиновым. Сверяй размеры с текущим baseline; не меняй
кадрирование всех картинок автоматически и не объявляй фиксированную область
собственным дефектом агента без сравнения с исходным компонентом.

После каждого блока возвращай IDs и компактные facts, проверяй bounds и
скриншот. Лимит ответа MCP проверяй в UTF-8 bytes; большие readback дели на
структуру, тексты и bindings, объединяй в локальном evidence. После ошибки
не повторяй весь документ; следуй сообщению инструмента и фактическому canvas.

## Граница качества

Проверка одного desktop не подтверждает mobile. Статическая кнопка не
подтверждает отправку формы или реальную скидку. Редактируемый макет и
его факты проверяются отдельно от визуального качества. При отсутствующем
подходящем компоненте/ассете или ограничении MCP сохраняй named gap и влияние
на результат. Пользователь выбирает изменение брифа; навык не меняет его сам.
