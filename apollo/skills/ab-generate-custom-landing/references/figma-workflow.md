# Источники и Figma workflow

Источник и обязательные начальные чтения заданы в [SKILL.md](../SKILL.md#начало-и-источники).
Здесь описаны маршруты к Hub и технические операции. Читай только раздел
текущего этапа: источники при выборе пакета, «До записи» перед первой операцией,
основу при её подготовке, операции с изображениями при наполнении.
Инструкции навыка и Figma API норм дизайн-системы не заменяют.

## От брифа к нужным источникам

| Решение | Начальный маршрут в ds-ai-hub |
|---|---|
| Черновой каркас, сетка и области | `products/ab/patterns/draft-layout.md`, `products/ab/components/corporate-content/` |
| Структура и цель лендинга | `products/ab/patterns/landing-pages.md` |
| Первый экран | `products/ab/components/promo-main-block/` |
| Бенефиты и ёмкость | `products/ab/components/benefits/`, `benefit-card/` |
| Содержательные секции | `benefits-block/`, другие компоненты выбранного паттерна |
| Форма/FAQ/файлы | Сначала допустимость и место по landing-pages, затем компонентные маршруты |
| Фон страницы | CorporateContent и mode `BackgroundPlate Color`; не палитра hero |
| Поверхность отдельного блока | `products/ab/components/background-plate/` и документы блока в Hub |
| Цвета и типографика | `core/common/tokens/`, `core/web/tokens/`, `manifest.sources.figmaTokens/figmaStyles` |
| Иконки | `core/web/assets/assets_glyph-26.json`; инструкции IconView по его маршруту |
| Иллюстрации | `products/ab/patterns/images_format.md`; указанные им каталоги Corp Image Library |

Из компонентной папки нужны `instructions.md`, `adapter.figma.md`, точные
`figma-keys.json` и применимые cookbook-разделы. Code adapter и bridge нужны
только если решение затрагивает код/cross-target, а не для обычной сборки Figma.
Не читай все компоненты. Обязательно читай constraints, applicability и public
boundary именно выбранного семейства. Сверь актуальный опубликованный key/API.

Proxy собирает маршруты из закреплённых Hub registry, component meta и графа.
Для текущего компонента он возвращает точные адреса обязательных документов,
дополнительные кандидаты и конкретные пробелы. Навигационные метаданные и hash
не подтверждают чтение норм: прочитай применимые исходные документы через reader.
Связи related/composes раскрывай по реальному контексту; они не делают весь граф
обязательным. Непрочитанный пакет не считается отсутствующим.

Внешние ссылки внутри Hub могут описывать происхождение данных. Не переходи
по ним к контрактам, техническим каталогам другого репозитория или сетевым
файлам. При отсутствии нужного key, API-факта, токена или ассета назови точный
пробел установленной Hub-проекции и его влияние; не подменяй источник.
Конфликт документов фиксируй, а не разрешай молча.

Различай прямое противоречие и более узкое совместимое условие. Если выбранная
конфигурация удовлетворяет обоим источникам, сохрани их расхождение и продолжай
в этой общей области. Например, отсутствие нормы про конкретный размер не
равнозначно запрету этого размера. Не блокируй всю страницу из-за конфликта
настройки, которая в этой композиции не используется. Реальное противоречие
выбранной конфигурации остаётся вопросом, а не разрешением обойти правило Hub.

## До записи

Решения о профиле размещения, сетке и интервалах прими по
[правилам лейаута](rules/page-layout.md) до сборки основы. Ниже — техническая
реализация выбранного решения; она не задаёт один каркас для всех форматов.

Шрифты загружай до text/variant/layout-операций.

- Получи Figma target; если файла нет — используй штатное создание с выбором
  команды по правилам инструмента. Создай session и переиспользуй её в follow-up.
- Прочитай target страницу без мутаций; сохрани baseline чужих roots.
- Для текущей основы/каркаса подготовь keys, публичные свойства, tokens/styles,
  fonts и структурные нормы. Источники точных текстов/ассетов готовь для текущего
  блока на этапе наполнения после завершения всех каркасов. Тип/роль подтверждай mapping,
  не одним названием слоя. Definitions варианта читай у owning component set.
- Сегмент и viewport определяются запросом/ответами и допустимым профилем,
  а не темой туров, произвольной палитрой или жёстким default из навыка.

## Основа отдельной страницы по паттерну

Прочитай применимый draft-layout и его компонентные источники. Выбор контейнера,
mount, сетки и отступов сохраняется из этих норм, а не из настроек generic Proxy.
Для паттерна, требующего CorporateContent, создай один CorporateContent и проверь, что всё содержимое страницы
попадает в его Body, SwapMe удалён, root сохраняет Fill/Hug и штатные bindings.

Разрешение заменить исходное содержимое Body берётся из рецепта самого
CorporateContent в установленном Hub. Через Figma MCP проверь фактический
свежесозданный экземпляр и источник: меняется только штатная неизменённая
заглушка, не пользовательское содержимое. При смене ID заново найди SLOT
от сохранённого корня; имя само по себе не доказывает принадлежность.
Перед первой записью в Body прочитай применимый рецепт CorporateContent
(`cookbook/02-desktop.md` для `[D]`): удали подтверждённую исходную заглушку
в указанном порядке, затем добавляй содержимое в фактический Body. Не считай
FRAME `SwapMe` instance-swap и не передавай SLOT в `setProperties`. Ошибка
одного способа не разрешает заменить обязательный CorporateContent обычным Frame.

После прерывания сначала прочитай фактический результат и продолжи имеющийся
блок, не создавая повторный Hero. Публичный блок и контент внутри него
подчиняются собственному рецепту и следующему этапу наполнения.
После вставки проверь sizing контейнера, Body и блока по источнику: штатный
размер пустого компонента не подтверждает размер наполненного каркаса.
Исправь непредусмотренное переполнение или явно зафиксируй незавершённость.
Grid & Cols mode задаётся на внешнем корне; вложенные системные узлы его
наследуют. Колонки, Content и Gutter бери из переменных; не путай ширину
viewport с шириной контентной области. Для Content/Isle используй Section
по его рецепту в Hub; простая вертикальная композиция может оставаться в Body.

Фон CorporateContent определяется разрешённым page mode, по умолчанию grey.
Внешний каркас прозрачен. `promo-classic` и `Appearance=Dark` главного блока
не задают цвет всей страницы. Host, containment, grid и page background
проверяются до детализации; отсутствие CorporateContent не является
допустимой экономией чернового прогона.

## Во время сборки

- Импортируй библиотечные компоненты по подтверждённым keys. Не detach и не
  копируй существующие локальные instances как источник новой сборки. Меняй
  только разрешённые component props, text overrides, slots и swaps.
- Только токены, текстовые и effect styles из источников хаба. Импортируй
  Variables/styles; не создавай собственные цвета, типографику и стили.
  Системные instances сохраняют штатные bindings. Прозрачные Auto Layout
  каркасы допустимы.

Один owned root, Auto Layout для связанного содержимого. Импортированные
instances сохраняются; компонентная геометрия и типографика не переписываются
ради размещения текста. Ширину и context modes задавай разрешённым рецептом способом.
После swap/variant/slot операции снова находи потомков от стабильного root ID.
Внутренние/imported IDs между MCP-вызовами не переиспользуются.

Для изображений предпочитай разрешённый swap компонента. Если нужен asset
transfer, используй существующий library source image → поддержанный export/
download/upload. Cross-file imageHash без проверки blob и рендера недостаточен.
В финальном результате не оставляй редакционную Grid, default asset или пустую
картинку вместо подобранного изображения. Временный placeholder каркаса до
этапа наполнения не считается законченным результатом.
Различай три уровня: Fill/Hug/Fixed узла, constraints Scale/Center внутри
родителя и scaleMode Fit/Fill/Crop растровой заливки. Scale у Image не делает
его внешний ImageView резиновым. Сверяй размеры с текущим baseline; не меняй
кадрирование всех картинок автоматически и не объявляй фиксированную область
собственным дефектом агента без сравнения с исходным компонентом.

После каждого блока возвращай IDs и компактные facts, проверяй bounds и
скриншот. Лимит ответа MCP проверяй в UTF-8 bytes; большие readback дели на
структуру, тексты и bindings, объединяй в локальном evidence. После ошибки
не повторяй весь документ; следуй сообщению инструмента и фактическому canvas.
Проверь target и свободное место; новый owned root создаётся один на прогон.
Учитывай фактический rollback receipt; неизвестное состояние сначала прочитай,
затем исправляй. Не создавай root повторно вслепую.

## Граница качества

Проверка одного desktop не подтверждает mobile. Статическая кнопка не
подтверждает отправку формы или реальную скидку. Редактируемый макет и
его факты проверяются отдельно от визуального качества. При отсутствующем
подходящем компоненте/ассете или ограничении MCP сохраняй named gap и влияние
на результат. Пользователь выбирает изменение брифа; навык не меняет его сам.


## Адресуемая справка Proxy

API symbols находятся в `workflow/figma-use/references/plugin-api-standalone.symbols.json`:
читай `symbols` → имя типа → offset/limit в указанном sourceResource. Индекс привязан
к SHA именно поставленных typings. Ссылки на компоненты/variables, validation/recovery
и componentization также поставлены как отдельные workflow resources; читай применимый
раздел перед операцией, не все документы в planning. Для конкретного изображения
сначала подтверди library source и поддержанный маршрут импорта/переноса и рендер;
imageHash или отсутствие отдельного download tool сами по себе не доказывают успех/отказ.
