# Прямой CLI-адаптер Apollo / Proxy

Читай этот документ при запуске навыка из Apollo. Это технический способ
работы, не источник норм дизайн-системы. Агент сам читает документы и создаёт
макет через Figma MCP. Плагин предоставляет чат и контекст выбранного файла;
Proxy запускает и продолжает CLI-сессию, сохраняет историю, checkpoint и usage.

## Источники

`apollo_knowledge.list_sources({query,offset})` ищет документы установленного
пакета. Запрос компонентной папки возвращает существующую маршрутизацию Hub:
обязательные и возможные документы, технические источники и конкретные гэпы.
Это навигация, не доказательство чтения норм.

`apollo_knowledge.read_source({id,mode,path,offset,limit})` читает документ:

- `id` — адрес из индекса, например
  `knowledge/data/ds-ai-hub/products/ab/components/corporate-content/instructions.md`;
- `mode=read` — содержимое, `mode=keys` — ключи JSON для дальнейшей навигации;
- `path=[]` для текста; для JSON — реально наблюдавшиеся ключи, не имена файлов;
- следуй `next` для продолжения диапазона, не считай большой непрочитанный файл
  отсутствующим. Ошибка/tooLarge не являются прочитанной нормой.

Документы навыка доступны под `selectedSkill.resourcesRoot`. Читай адресные
разделы по таблице SKILL.md перед текущим действием, не все references сразу.
Технические инструкции — `workflow/figma-use/SKILL.md`,
`workflow/figma-generate-design/SKILL.md` и нужные references того же workflow.
Источники норм/ключей/ассетов — только пакетная DS AI HUB проекция; доступ
к raw Git, локальным навыкам автора, контрактам и другим репозиториям отсутствует.
Shell, apps/plugins, веб-поиск и автоматические локальные навыки выключены
при каждом новом запуске CLI и при resume. Самостоятельно их не подключай.

## Сборка

Выполняй порядок SKILL.md непосредственно через `apollo_figma_mcp`.
Создай/переиспользуй один корень внутри переданной страницы или выбранной секции.
Контейнер, Body, сетка, режимы и отступы следуют прочитанным источникам;
Proxy не задаёт их значения. Перед каждым изменением разреши фактический root
и проверь его принадлежность. До чтения/записи выполни технический Figma workflow,
включая сессию файла, загрузку шрифтов и public API.

При `placement.mode=new-section` owned root — новый SECTION прямо на странице;
layout-wrapper и компоненты находятся внутри него. При `placement.mode=section`
owned root — новый FRAME прямо внутри выбранной секции. В target возвращается
этот внешний owned root, а не вложенный wrapper.

На новом root сразу запиши namespace `apollolanding`: `chat=chatId`,
`owner=ownerNonce`. Перед созданием ищи такой root среди детей переданного
родителя: один существующий переиспользуется, неоднозначность останавливает запись.
Из изменяющего или проверочного `use_figma` верни фактические affected IDs и:

```json
{"target":{"rootNodeId":"actual-id","pageId":"actual-page","parentNodeId":"actual-parent","ownerNonce":"provided-nonce"}}
```

Корень и его родитель не переназначаются по догадке. Вложенные ID могут меняться:
перечитай дерево от owned root и заново найди нужный SLOT/компонент.
Не удаляй существующее пользовательское содержимое для восстановления.
При неизвестном результате сначала прочитай canvas; повторять создание вслепую нельзя.

После вставки проверь реальные type/key, варианты, slots, размеры и sizing.
Размеры пустой основы не подтверждают наполненный Body. Непредусмотренное
переполнение исправляется по источнику или остаётся явной незавершённостью.

## Пауза и продолжение

После каркаса остановись и верни `needs-structure-approval`, ссылку на root
и понятное описание структуры. Proxy не запускает наполнение до явного решения
пользователя. «Продолжай» само по себе согласованием не считается.
При отказе меняется только запрошенная структура, затем требуется новое решение.
Перед наполнением перечитай root и сопоставь с показанным checkpoint; внешние
изменения структуры требуют повторного согласования.

Stop останавливает CLI, сохраняет partial outcome и фактически полученные IDs.
Продолжение использует тот же CLI sessionId и сначала читает фактический макет.
История прежнего механизма доступна только для чтения/удаления из списка;
его выполнение и старые canvas callbacks не возобновляются.

## Ответ и отчёт

Возвращай небольшое состояние текущего шага, не полный технический план:

```json
{
  "status":"needs-structure-approval",
  "message":"Каркас создан. Структура подходит или нужно изменить её?",
  "rootNodeId":"actual-id",
  "checkpoint":"Что собрано, какие решения приняты и что делать дальше",
  "checks":[],
  "issues":[]
}
```

`needs-input` — существенный вопрос; `needs-structure-approval` — ожидание
пользователя после каркаса; `partial` — сохранённый незавершённый шаг;
`completed` — весь запрошенный результат после согласования и наполнения.
Проверки имеют `name`, `status=passed|failed|unknown`, `evidence`.
Успешный вызов MCP не является полной DS-приёмкой. Проверки агента так и помечаются;
неполученные изображения не являются визуальной проверкой, Ready не утверждается.
Фактический usage и прочитанные источники сохраняет Proxy из событий CLI/MCP.
