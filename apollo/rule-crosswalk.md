# Apollo RuleID Crosswalk

## Зачем нужен crosswalk

Решение владельца от 06.11.2026: одна и та же подтверждённая норма использует
**один RuleID из ds-ai-hub** в документации, исполняемых данных и результате Apollo.

- **human RuleID** в Hub обозначает понятную человеку дизайн-политику;
- **RuleID Apollo** для этой нормы совпадает с human RuleID; ID конкретной проверки
  (`contractId`, `constraintId`) остаются отдельными техническими полями.

Несколько технических проверок могут исполнять одну норму. Это не основание создавать
для неё разные нормативные ID. Технические классификации без соответствующей нормы
и неоднозначные отношения не переименовываются автоматически.

`rule-crosswalk.json` — единственный мост между этими уровнями. Он не участвует в verdict
predicate-движка и не заменяет `rules.json`; он позволяет аудитам, таблице «Правила» и
агентам показать доказательство без ложного `Missing`.

## Модель v2

Каждая запись связывает один `apolloRuleId` с `hubEvidence[]` и имеет отношение:

| Relation | Значение |
| --- | --- |
| `exact` | Смысл и гранулярность совпадают полностью. |
| `semantic-equivalent` | Смысл совпадает, но техническая проверка уточняет owner, focus или property. |
| `semantic-support` | Human-документ описывает правило в section, но не выделяет самостоятельный RuleID. |
| `technical-only` | Внутренняя классификация/транспорт Apollo; отдельная human-политика не нужна. |
| `conflict` | Источники существуют, но противоречат друг другу. Это review-queue, а не `Missing`. |

Типы `hubEvidence`:

- `named-rule` — обязательно содержит `ruleId`, документ и заголовок;
- `section` — содержит документ и заголовок, если human RuleID не выделен;
- `technical-only` — записывается пустым `hubEvidence[]` только вместе с relation
  `technical-only`;
- `conflict` — содержит минимум два доказательства и фиксирует конкретное расхождение.

Связи 1:N и N:1 допустимы. Например, несколько Apollo RuleID могут ссылаться на один
human RuleID; одна техническая проверка также может агрегировать несколько human-политик.

## Порядок обновления

Для подтверждённой миграции запиши `canonicalRuleId`, совпадающий с `apolloRuleId`
и конкретным `named-rule` хаба. Старые ID перенеси в `legacyApolloRuleIds`, не
оставляя вторую активную норму. В `executionSources` перечисли исполняемые привязки.
Текущий V3 формирует ID композиционного результата как `contract.id + '.' +
constraint.id`: проверь это равенство canonical RuleID, одного поля `constraint.ruleId`
недостаточно. Правильный и ошибочный примеры должны сохранять прежние verdict.
Штатный crosswalk-тест проверяет принятую миграцию и отклоняет рассинхрон.
Остальные записи v2 остаются историческими/неперенесёнными; наличие одной принятой
связи не означает синхронизацию всего реестра.

1. Добавить или изменить machine rule в `JSONS/**/rules.json`.
2. Найти human-доказательство в `ds-ai-hub`: сначала `ruleId`, затем section инструкции,
   cookbook или adapter.
3. Добавить проверенную связь в `apollo/rule-crosswalk.json`. При совпадающей норме
   перенести Hub RuleID в исполняемые данные; не добавлять технические ID в Markdown хаба.
4. Запустить `node --test test/rule-crosswalk.test.js` из `services/apollo-proxy`.
   Тест проверяет существование Apollo RuleID, документа, human RuleID/заголовка и полное
   покрытие manual-правил AmountStyles — пилотного компонента.
5. Обновить строки «Правила» и при необходимости «Леджер»: `Missing` разрешён только после
   проверки crosswalk. Отсутствующая формальная метка RuleID при существующем section — это
   `semantic-support`, а не `Missing`.

## Границы ответственности

- Predicate-движок принимает verdict только по исполняемым правилам и фактам Figma.
- Hub остаётся источником человеческой инструкции и объяснений.
- Crosswalk обеспечивает трассируемость и не меняет runtime-поведение Apollo, поэтому его
  обновление не требует перепаковки proxy. Перепаковка нужна только при изменении правил,
  runtime-кода или пакета знаний, который читает proxy.
