# Подготовка исполняемых правил V3

Для владельца вход — компонент и формулировка нормы обычным языком, в этом чате.
Агент использует следующий процесс и сохраняет проверяемый результат; вручную
редактировать JSON или помнить названия операторов владельцу не требуется.

1. Найти компонент и уже существующие правила. Сначала изменять существующий
   RuleID; новое правило добавлять только при новой уникальной норме.
2. Уточнить источник нормы и область действия: корень/вложенный слой, платформа,
   варианты, видимость, границы Slot/swap и исключения. Проверить, какие факты
   уже есть в raw-каталоге и что действительно читает V3.
3. Назвать способ исполнения и предел поддержки. Если существующего оператора,
   данных или сценария авторинга не хватает, указать конкретный пробел.
   Отсутствие проверки не превращать в разрешение или в успешную приёмку.
4. Подготовить candidate и понятный preview: RuleID, источник, область действия,
   старое/новое значение, положительный и отрицательный пример. Оба примера
   выполнить действующим V3 evaluator; проверить чужой/неподходящий контекст.
5. Перенести проверенную норму в исходник с проверкой source SHA, синхронизировать
   учёт и пересобрать обычный пакет данных Proxy. Применение исходника,
   публикация/обновление данных и ручная Figma-проверка — отдельные статусы.

## Что уже работает

| Вид | Исполнение V3 | Авторинг этим инструментом |
|---|---|---|
| Количество вложений | `countBetween` | Анкета, candidate/diff и примеры |
| Свойство совпадает с эталоном | Существующие diff/assessment/report V3 | `propertyBaseline`: `rules.json`, анкета, candidate/diff и примеры |
| Числовые границы размеров | Существующий `numericConstraint` V3 | `propertyRange`: `rules.json`, анкета, candidate/diff и примеры |
| Домены, равенство свойств, порядок | Есть существующие composition evaluators | Пока просмотр; изменение явно не поддержано |
| Другие правила слоёв из `rules.json` | Зависит от конкретного механизма V3 | Пока просмотр; наличие нормы не доказывает применимость к узлу |
| Ссылки на контекстные паттерны | Зависит от конкретного правила и фактов | Показывается ссылка; детерминированное исполнение не обещается |

`inspect` показывает фактическую проекцию пакета, источники определений и
объявления, не попавшие в эту проекцию. Если manual перекрыт runtime, это видно
по отличию определения от effective. Поддержка типа в анкете отмечается отдельно
от результата проверки; при просмотре `examplesVerified=false`.

Рабочий инструмент — `apollo/scripts/v3-rule-author.cjs`. Он создаёт черновик
`composition-contract.json` или `rules.json`, нормализует его настоящим кодом
Apollo и выполняет примеры. Исходные нормы не меняет и ничего не публикует.

Поддержаны `countBetween`, `propertyBaseline` и `propertyRange`. Другие виды
нельзя получить произвольным текстом: нужен проверенный сценарий поверх
существующего исполнителя V3.

## Подключение

Нужны соседний checkout `Apollo` и его зависимости (`npm ci` в Apollo).
Укажи `APOLLO_ROOT` или передавай `--apollo-root /path/to/apollo`. Абсолютный путь
автора не зашит в инструмент. Figma, Proxy, ключ активации и сеть не нужны.
Чистые модули V3 компилируются в памяти; `dist` и сборка плагина не меняются.

```sh
export APOLLO_ROOT=/path/to/apollo
node apollo/scripts/v3-rule-author.cjs kinds
node apollo/scripts/v3-rule-author.cjs list
node apollo/scripts/v3-rule-author.cjs inspect --component web-corp.buttons-group
node apollo/scripts/v3-rule-author.cjs interview
```

`inspect` ничего не записывает. Его JSON содержит формулировку, RuleID,
селектор, source-файл/JSON pointer, authority/checkType и доступность сценария
авторинга. Агент переводит эти поля в карточку правила для владельца.
Внешние ссылки на паттерны и смысловые дубликаты автор сверяет отдельно.

В анкете можно найти компонент по части имени или componentKey. При нескольких
совпадениях выбери номер либо точный ключ. Затем выбери поддержанное условие,
группу и правило из списка; пункт `+new` создаёт новую группу или правило.
Неподдержанные условия показаны отдельно и сохраняются без изменений.

При изменении сохраняются стабильные ID и селектор группы. Текущие минимум,
максимум и формулировка предложены по умолчанию: Enter сохраняет значение.
Для новой группы нужны точные имена владельца и вложенного компонента,
видимость, границы и полная норма. До сохранения показывается полный RuleID V3.
Источник нормы и новая папка результата обязательны. Дубликат ID не создаётся.
Ключи Figma или заранее известные ответы можно передать параметрами `interview`
или `create`. Существующий ID другого типа в countBetween не преобразуется.

## Воспроизводимая команда для агента

Значения ниже — пример синтаксиса, не согласованная новая норма ButtonGroup.
Не применяй их к рабочим данным без проверки нормативного источника.

```sh
node apollo/scripts/v3-rule-author.cjs create \
  --component web-corp.buttons-group \
  --kind countBetween \
  --contract buttons-group.desktop-composition \
  --id button-count --min 2 --max 4 \
  --message 'В desktop ButtonsGroup должно быть от двух до четырёх видимых кнопок' \
  --source 'путь/к/согласованному/источнику#раздел' \
  --output /tmp/new-v3-rule-candidate
```

Для новой группы дополнительно нужны `--host-key` или `--host-name`,
`--member-key` или `--member-name`, при необходимости `--visibility visible|all`.
Для существующего правила сохраняется остальное содержимое и соседние правила.
Если у него есть presentation, ожидание обновляется из нормы; действие можно
задать через `--action`, иначе используется та же формулировка. Все изменения
показаны в diff. Правило другого типа инструмент не перезаписывает.

## Результат и предел проверки

Для `rules.json` поддержаны два сценария без добавления операторов V3:

- `propertyBaseline`: точное свойство `radius`, `opacity`, `layout.width`,
  `layout.height`, `layout.itemSpacing`, четыре `layout.padding.*`, `styles.text`,
  `fill` или `stroke` совпадает с эталоном. Ширина/высота — только Fixed; интервал
  — при двух видимых детях. Hug/Fill и пустой контейнер проверяются как
  неприменимые, а не как PASS. Заливки в примерах представлены ID токенов,
  текстовые стили — ID стилей. IMAGE/GRADIENT этим сценарием не подтверждаются.
- `propertyRange`: одно из `layout.width`, `layout.height`, `layout.minWidth`,
  `layout.maxWidth`, `layout.minHeight`, `layout.maxHeight` удовлетворяет
  `numericConstraint.minimum/maximum`. Границы включительные. Диапазон
  не является сравнением физического размера с baseline.

Это точные безусловные правила для root или названного слоя. Смена существующего
свойства/селектора, условия по вариантам, Slot-селекторы, required/token/domain
нормы, inactive/manual правила и recommended-ограничения пока отклоняются.
Работа с ними не подменяется подходящим по названию типом.

В примерах имя владельца берётся из независимо прочитанного `packageName`, а
ключ — из `figmaKeys` индекса. Имя из проверяемого селектора не подставляется
как доказательство его применимости: несовпадение приводит к отказу кандидата.

```sh
node apollo/scripts/v3-rule-author.cjs create \
  --kind propertyBaseline --component web-core.input \
  --id component:web-core.input.example-radius --property radius --layer root \
  --baseline 10 --invalid-value 999 \
  --message 'Синтетический пример: radius совпадает с эталоном' \
  --source 'synthetic:example-only' --output /tmp/radius-candidate

node apollo/scripts/v3-rule-author.cjs create \
  --kind propertyRange --component web-core.input \
  --id component:web-core.input.example-width --property layout.width \
  --min 100 --max 400 --valid-value 200 --invalid-value 401 \
  --message 'Синтетический пример: ширина от 100 до 400' \
  --source 'synthetic:example-only' --output /tmp/width-candidate
```

Команды показывают синтаксис, а не утверждают новые нормы Input. Если такое
свойство уже запрещено существующей нормой, создание дубликата будет отклонено.
Для воспроизводимых примеров используй синтетический компонент или согласованную
конкретную норму. `--baseline` задаёт тестовый факт, не фиксированное значение
в правиле: реальный baseline берётся существующим Apollo из каталога.

Для изменения передай прежний полный `--id`. Селектор, соседние нормы и
незатронутые поля сохраняются. Generated-норма изменяется через manual override
с тем же RuleID, generated остаётся нетронутым. Runtime overlay и дубликаты
RuleID/одинаковой нормы останавливают создание кандидата. Изменённая активная
норма получает следующую revision в кандидате; это не применение к production.

Примеры проходят `preparePolicies`, реальный diff или numeric producer,
применение V3 overrides/assessment и `buildApolloStatsReport`. Ошибочный пример
обязан выдать violation именно выбранного RuleID. Каждый заявленный слой
проверяется отдельно; чужой компонент — отрицательный контроль применимости.
Отсутствие фактов, UNKNOWN и неприменимость не принимаются за успешный пример.

В output появятся `rules.candidate.json`, `report.json` и `preview.md` с
источником, RuleID, условием, селектором, diff и результатами примеров.

Для `countBetween` в новой папке будут:

- `preview.md` — формулировка и фактический RuleID V3.
- `composition-contract.candidate.json` — исходный документ с изменением.
- `report.json` — source SHA, кандидат SHA, семантический diff, нормализованное
  правило, граничные примеры и контроль селектора через существующий comparator.

В preview также видны селектор, diff и два проверенных примера: допустимое
количество без нарушения выбранного правила и недопустимое количество с
нарушением его RuleID. Это синтетические примеры количества, а не Figma-кейсы.
`--kind` необязателен для прежних команд `create`; его значение по умолчанию —
`countBetween`. Неподдержанный тип явно отклоняется, а не подменяется другим.

На границах проверяется существующий оператор по факту количества. Отдельное
маленькое синтетическое дерево проверяет выбор прямых вложенных INSTANCE,
видимость и исключение внуков; чужой владелец обозначается `NOT_APPLICABLE`.
Это проверка выбранной нормы, а не всех правил/платформ компонента. Пустой список
нарушений не называется универсальным PASS. Если runtime перекрывает manual и
кандидат не попадает в исполняемую проекцию, инструмент отказывает.

Перед сохранением повторно сверяются данные и прочитанные исходники Apollo.
Изменение выбранного исходника или индекса во время анкеты либо перед созданием
кандидата останавливает запись: нужно повторить выбор на актуальных данных.
Существующий output, source вне репозитория, неподдерживаемый формат и невалидный
диапазон не перезаписываются. В `JSONS` результат не записывается.

После ревью кандидата автор переносит согласованную норму в исходник с проверкой
source SHA. Для настоящего изменения нормы действуют `AGENTS.md`: строки
«Правила», при расхождении «Леджер», Predicate → Draft и повторное чтение таблиц.
Затем запускается существующая сборка данных Proxy. Публикация и ручные кейсы
Figma — отдельные действия. Инструмент сам эти шаги не выполняет.
