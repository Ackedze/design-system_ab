# ComponentContract Editor — инструкция пользователя

Эта инструкция относится к экспериментальному MVP. Плагин редактирует ручной
слой контракта одного компонента и автоматически создаёт исполняемый артефакт
для Apollo.

## Что получается в результате

В редакторе автор описывает:

- стабильный component ID, назначение и границы применения;
- Figma/code representations и единый semantic API между ними;
- ссылки на документацию, примеры, решения и профили генерации;

- какую часть компонента регулирует правило;
- какое свойство или группу свойств оно охватывает;
- разрешено ли изменение;
- через какой публичный путь им можно управлять;
- какие ограничения действуют;
- для каких variants и modes применяется правило;
- severity, rationale, owner и remediation intent.
- отдельный execution route: predicate, policy-only, delegated или context-only.

Пользователь не редактирует RuleIR, coverage, runtime policy и compiled JSON.
Эти части создаются компилятором.

Основная формула правила:

```text
semantic target
  → capability
  → permission
  → control path
  → typed constraint
  → applicability
  → execution route
```

## 1. Установка development-плагина

1. Откройте Figma Desktop.
2. Выберите **Plugins → Development → Import plugin from manifest…**.
3. Укажите файл:

   ```text
   projects/figma-plugins/ComponentContractEditor/manifest.json
   ```

4. Запустите **ComponentContract Editor** из списка development-плагинов.

Собранные файлы уже находятся в `dist`. После изменения исходного кода плагин
нужно пересобрать:

```bash
cd projects/figma-plugins/ComponentContractEditor
npm run build
```

## 2. Что импортировать

Для первой сессии используйте один компонентный Athena-пакет.

### Button

```text
shared/design-system_ab/JSONS/web/components/web-core/core/Button/
```

### CorporateContent

```text
shared/design-system_ab/JSONS/web/components/web-corp/CorporateContent/
```

Нажмите **Импорт** и выберите все JSON-файлы внутри нужного каталога. Также
можно передать ZIP, содержащий эти JSON-файлы.

Рекомендуемый состав пакета:

- `contract.generated.json`;
- `contract.overrides.json`;
- `semantic-targets.json`;
- `composition-contract.json`;
- `rules.json`;
- `examples.json`;
- `audit-mapping.json`;
- `agent-context.json`.

Не загружайте большой raw-файл `Web _ Core -- Button.json` или
`Web _ Corp Components -- CorporateContent.json`. Это источник Athena, а не
рабочий файл Editor.

Импорт существующего `component-contract.v2.json` поддерживается, но такой файл
считается только read-only evidence. Из compiled JSON нельзя достоверно
восстановить утраченное авторское намерение.

## 3. Устройство окна

### Верхняя строка — Preview scenario

Здесь показываются имя компонента, его библиотека, текущая revision и
переключатели доступных component properties. После живого рендера здесь также
появляются найденные variable collections и их modes.

Если Athena package содержит несколько платформенных main-компонентов одного
семейства, первым отображается переключатель **Компонент** — например
`[D] Button · desktop` и `[M] Button · mobile-web`. Preview и componentKey
меняются, но при импорте одного semantic manual source все representations
редактируют тот же `contract.manual.json`.

Кнопка **Паспорт** открывает поля всего компонента: identity, semantics,
representations, semantic API, documentation refs, examples, normative
decisions и generation profiles. Большие структурированные блоки редактируются
как JSON и валидируются перед сохранением.

Изменение variant или mode запускает новый preview и новый factual snapshot.

### Левая колонка — Anatomy

Это фактическое дерево импортированного экземпляра:

- `C` — component или instance;
- `T` — text;
- `F` — frame или group;
- `S` — slot;
- `L` — другой слой.

Нажатие на строку выбирает область действия будущего правила. Поиск сверху
фильтрует дерево по имени, пути и semantic role.

Цветной индикатор справа показывает устойчивость semantic target:

| Цвет | Состояние | Значение |
|---|---|---|
| Зелёный | `resolved` | Цель однозначно найдена. |
| Жёлтый | `ambiguous` | Найдено несколько подходящих узлов. |
| Жёлтый | `unknown` | Для сопоставления пока недостаточно evidence. |
| Красный | `missing` | Цель была в manual source, но отсутствует в текущем экземпляре. |

Перед переводом правила в `reviewed` желательно устранить `ambiguous` и
`missing`.

### Общая цветовая легенда

| Область интерфейса | Цвет | Значение |
|---|---|---|
| Индикатор в верхней панели | Серый | Плагин ждёт импорт или действие. |
| Индикатор в верхней панели | Синий, пульсирующий | Идёт импорт или построение preview. |
| Индикатор в верхней панели | Зелёный | Manual source валиден и готов. |
| Индикатор в верхней панели | Жёлтый | Есть предупреждения или контракт требует внимания. |
| Левая граница Typed constraint | Чёрная | Permission `forbidden`. Constraint заменён проверкой baseline. |
| Левая граница Typed constraint | Зелёная | Permission `allowed`. Это policy-only правило. |
| Левая граница Typed constraint | Красная | Permission `constrained`. Constraint будет скомпилирован в RuleIR. |
| Результат Test | Зелёный | `compliant`. Проверка пройдена. |
| Результат Test | Красный | `violation`. Найдено нарушение. |
| Результат Test | Жёлтый | `human-review` или `not-evaluable`. Evidence недостаточно. |
| Всплывающее сообщение | Красная граница | Ошибка операции или validation. |
| Всплывающее сообщение | Жёлтая граница | Некритичное предупреждение. |

Цвет всегда дублируется текстом или статусом — он не является единственным
носителем информации.

### Центральная колонка — Evidence

Здесь находится PNG-preview фактического экземпляра. Он создаётся на временной
служебной странице Figma. После получения изображения и snapshot временный
instance и страница удаляются даже при ошибке.

Под preview находится **Observed facts** выбранного узла. Нажатие на свойство
переносит его путь в поле Capability справа. Это основной способ создавать
правило без знания JSON.

#### Работа с текстовым узлом

Да, текстовый узел можно выбрать в Anatomy. Он обозначен буквой `T`.

После выбора в Observed facts доступны, в зависимости от evidence:

- `text.characters` — фактическое текстовое значение;
- `text.fontSize`;
- `text.fontName.family` и `text.fontName.style`;
- `text.lineHeight`;
- `text.letterSpacing`;
- `text.case`;
- typography и fill facts из раздела `appearance`.

Чтобы проверить конкретное значение текста:

1. Выберите узел `Label` или другой TEXT-узел.
2. Нажмите `text.characters` в Observed facts.
3. Выберите permission **С условиями**.
4. Выберите constraint **Допустимые значения**.
5. Введите разрешённые строки через запятую.

Для Button чаще правильнее регулировать не внутренний `text.characters`, а
публичное `component-property.*`, через которое меняется label. Тогда target
может оставаться текстовым узлом, capability описывает публичное свойство, а
control path выставляется в `Host property`. Прямой контроль
`text.characters` используйте только тогда, когда контракт действительно
разрешает или запрещает редактировать внутренний TEXT-слой.

### Правая колонка — Author

Здесь создаётся ручное нормативное правило. Колонка прокручивается независимо
от preview.

Правая колонка имеет два отдельных состояния:

1. **Правила компонента** — просмотр всех существующих правил и быстрых
   действий. Нажмите карточку правила, чтобы открыть её, либо `+`, чтобы создать
   новое.
2. **Новое правило / Изменение правила** — детальная форма. Стрелка в заголовке
   возвращает к списку, не удаляя preview и snapshot.

В состоянии просмотра доступно быстрое действие **Защитить внутреннее
устройство**. Оно создаёт или обновляет два обычных manual rules: запрет
`auto-layout@1` и `visual-style@1` на корневом target вместе со всеми потомками.

Публичные component properties настраиваются через те же карточки правил и
детальную форму. Отдельного параллельного редактора публичных свойств нет.

Быстрые действия не создают отдельный формат и не изменяют generated facts.
Они записывают те же canonical manual rules, которые видны в детальном
редакторе и компилируются общим compiler core.

В карточке правила отображаются permission, status, semantic target, scope и
**Variants**. Значение **Все** означает действие на все варианты; для
ограниченного правила показывается сохранённая комбинация, например
`View=Primary · Size=56`.

Нажатие на карточку загружает правило в детальную форму, но не перестраивает и
не удаляет preview. Метка **Preview закреплён** означает, что текущие
изображение, anatomy и snapshot остаются контекстом редактирования. После
сохранения Editor возвращается к списку правил, а затем можно сразу повторно
нажать **Проверить preview** или
**Проверить выделенный instance**.

Если поверх открытого компонента импортировать `contract.manual.json` того же
семейства, библиотеки и платформы, Editor заменит только manual-слой и сохранит
текущий preview/snapshot. В новой сессии один `contract.manual.json` сам по себе
не содержит изображения: сначала возьмите instance из Figma либо импортируйте
Athena package с variant evidence.

### Нижняя строка — Test & compile

Здесь отображаются validation status, число созданных RuleIR и предупреждения.
Кнопка **Compiled JSON** открывает только read-only представление результата.

## 4. Создание правила

### Шаг 1. Выберите target

Нажмите компонент, слот или слой в Anatomy. Editor создаст либо переиспользует
semantic target. Контракт не опирается только на нестабильный `nodeId`: также
сохраняются semantic role, path, lineage, имя и structural fingerprint.

### Шаг 2. Выберите группу и свойства

Самый безопасный способ — нажать фактическое свойство в **Observed facts**.

Типовые capability:

```text
appearance.fill
appearance.stroke
appearance.opacity
appearance.radius
layout.mode
layout.itemSpacing
layout.padding.top
component-property.View
visibility
```

Сначала выберите **Группу**:

- **Одно свойство** — обычное capability выбирается в поле **Свойство слоя**, а
  публичное свойство экземпляра — отдельно в поле **Component Property**;
- **Заливка** — paint-значение и локальный paint style;
- **Обводка** — paint, style, толщина, выравнивание и dash pattern;
- **Автолейаут** — направление, отступы, интервалы, выравнивание и sizing;
- **Скругление** — радиусы;
- **Эффекты** — эффекты и effect style;
- **Внешний вид** — единая группа основных визуальных параметров:
  заливка, обводка, прозрачность, скругление и эффекты.

В UI версии групп не показываются. В manual source они по-прежнему сохраняются
как `fill@1`, `stroke@1` или `visual-style@1`: суффикс фиксирует состав группы и
не даёт будущему обновлению незаметно изменить уже созданный контракт.

Суффиксы Figma вида `#4:8` у Component Property также скрыты в UI. Это
внутренние идентификаторы, которыми Figma различает свойства с одинаковыми
именами; Editor сохраняет их в контракте, но показывает автору только понятное
имя — например **Hint**.

После выбора семантической группы Editor показывает её свойства чек-листом.
Изначально выбраны все свойства; ненужные можно снять. В manual source
сохраняется `capabilitySelection`, а compiler создаёт RuleIR только для
выбранного подмножества. Пустую группу сохранить нельзя.

**Внешний вид** является полноценной рабочей группой. Используйте её,
когда правило должно защищать визуальный образ слоя целиком. Отдельные группы
заливки, обводки, скругления и эффектов удобнее, когда требуется более узкое
правило.

Группа — это стабильный набор capabilities. Она не означает «все свойства
компонента навсегда».

В поле **Область действия** задаётся, к каким слоям применяется правило:

- **Только выбранный слой** — проверяется semantic target;
- **Слой и все его потомки** — проверяются target и все вложенные слои. Этот
  scope подходит, например, для запрета автолейаута или внешнего вида во всём
  внутреннем устройстве компонента.

При групповом запрете Editor проверяет capability только на тех слоях, где оно
присутствует в effective baseline. Отсутствующее у данного типа слоя свойство
не считается нарушением. При этом явное значение `null` считается
присутствующим и нормативным: например, `stroke: null` означает, что обводки
быть не должно. Если такое свойство удалить или заменить ненулевым значением,
проверка вернёт violation.

### Шаг 3. Назначьте permission

#### Запрещено

Свойство нельзя менять вручную. Для свойства слоя compiler автоматически
создаёт проверку на совпадение с effective baseline текущего variant/mode.
Для boolean **Component Property** (например `Hint`) запрет означает, что
property должна быть выключена: допустимо только `false`. Это выражает именно
«Hint использовать нельзя», а не только «Hint нельзя менять».

Для полностью запрещающего правила выставьте:

| Поле | Значение |
|---|---|
| Target | Компонент, слот или слой, свойство которого защищается. |
| Область действия | **Только выбранный слой** либо **Слой и все его потомки**. |
| Capability | Запрещаемое свойство или версия группы свойств. |
| Permission | **Запрещено**. |
| Control path | Не заполняется и блокируется интерфейсом. |
| Typed constraint | Для слоя не заполняется; compiler использует effective baseline. Для boolean Component Property Editor сохраняет допустимое значение `false`. |
| Severity | Обычно `error`; `warning`, если отклонение временно допустимо. |
| Status | `draft` во время настройки, затем `reviewed`. |
| Owner | Команда-владелец правила. |
| Rationale | Обязательно для `reviewed`: почему изменение запрещено. |
| Remediation intent | Необязательно; например `restore-effective-baseline`. |

Запрещающее правило действует на изменение capability независимо от способа,
поэтому у него нет разрешённого control path.

#### Разрешено

Изменение допустимо через заданный control path. Это policy-only запись: она
попадает в `customizationPolicy`, но не создаёт бессмысленный RuleIR.

Для разрешающего правила используйте:

| Поле | Что вводить |
|---|---|
| Target | Область, которую разрешено настраивать. |
| Область действия | **Только выбранный слой** либо **Слой и все его потомки**. |
| Capability | Конкретное свойство или версионированная группа. |
| Permission | **Разрешено**. |
| Control path | Реальный публичный способ управления: `Direct`, `Host property`, `Slot API` и т. п. |
| Property / port | Заполняется для выбранного пути; для `Direct` можно оставить пустым. |
| Другие пути запрещены | Включить, если разрешён только указанный путь. |
| Typed constraint | Не заполняется и блокируется интерфейсом. |
| Severity | Рекомендуется `info`: это metadata политики, а не severity violation. |
| Status | `draft` до подтверждения, затем `reviewed`. |
| Owner | Владелец разрешения, обычно `design-system-authors`. |
| Rationale | Для `reviewed` обязательно объяснить, зачем customization разрешён. |
| Remediation intent | Обычно оставить пустым: нарушение не создаётся. |

Applicability всё равно важно: разрешение может действовать для всех variants
либо только для текущей комбинации.

#### С условиями

Изменение разрешено только при выполнении typed constraint. Именно этот режим
используется для разрешённых доменов значений, диапазонов, количества,
отношений и token bindings.

### Шаг 4. Укажите control path

Permission отвечает на вопрос «можно ли менять», а control path — «как именно
этим разрешено управлять».

| Control path | Когда использовать |
|---|---|
| `Direct` | Свойство разрешено менять непосредственно на target. |
| `Host property` | Управление идёт через component property родительского компонента. |
| `Nested property` | Используется публичное свойство вложенного instance. |
| `Slot API` | Управление происходит через содержимое или конфигурацию слота. |
| `Variable binding` | Значение задаётся binding на разрешённую variable. |
| `Inherited port` | Владение передаётся наружу через локальный control port компонента. |

Если включено **Другие пути запрещены**, указанный путь считается единственным
допустимым способом изменения.

`Inherited port` не превращает внешнего владельца в часть ComponentContract.
Плагин создаёт только локальный порт. Кто именно подключён к нему, позже
определяет PatternContract.

### Шаг 5. Задайте typed constraint

Typed constraint применяется для permission **С условиями**.

| Тип | Назначение |
|---|---|
| Допустимые значения | Значение должно входить в заданный список. |
| Наличие / отсутствие | Target должен присутствовать или отсутствовать. |
| Совпадает с baseline | Свойство не должно отличаться от effective baseline. |
| Количество | Число элементов с semantic role должно попасть в диапазон. |
| Порядок | Прямые дочерние элементы должны идти в указанной последовательности. |
| Связь элементов | Проверяет parent/ancestor/child/descendant/before/after/adjacent. |
| Token binding | Требует binding и, при необходимости, один из разрешённых token IDs. |
| Layout constraint | Проверяет точное значение или числовой диапазон. |

Значения в списке разделяются запятыми. `true`, `false`, `null` и числа
сохраняются как типизированные значения, а не строки.

### Шаг 6. Настройте applicability

- **Variants → Все** — правило действует на все варианты компонента.
- **Variants → Текущий** — Editor сохраняет выбранную комбинацию properties.
- **Modes → all** — правило не ограничено конкретным mode.

В текущем MVP для первого пилота рекомендуется оставлять поле Modes равным
`all`. Переключение mode уже влияет на preview и baseline, но окончательная
нормализация mode-scoped conditions между Athena и Apollo ещё требует отдельной
golden-проверки.

### Шаг 7. Заполните служебные поля

- **Severity** — `error`, `warning` или `info`.
- **Status** — `draft`, `reviewed` или `deprecated`.
- **Owner** — владелец ручного правила.
- **Rationale** — почему правило существует.
- **Remediation intent** — безопасное намерение исправления, а не произвольный
  исполняемый код.

Для `reviewed` обязательно заполнить Rationale. Пока правило находится в
`draft`, весь compiled contract также остаётся `draft`.

Нажмите **Сохранить правило**. Editor вернёт вас к основному списку правил, не
удаляя текущий preview.

## 5. Четыре базовых сценария

### Запретить ручной radius

1. Выберите корневой слой компонента.
2. Capability: `appearance.radius`.
3. Permission: **Запрещено**.
4. Control path и typed constraint не заполняйте — они будут заблокированы.
5. Severity: `error`.
6. Status: сначала `draft`, после проверки `reviewed`.
7. Опишите rationale и сохраните правило.

Apollo будет сравнивать radius с effective baseline текущего состояния.

### Разрешить изменение текста Button

1. Выберите текстовый слой Button.
2. Нажмите соответствующий observed fact либо выберите публичное
   `component-property.*`.
3. Permission: **Разрешено**.
4. Выберите `Host property`, если текст должен меняться через property Button.
5. Введите имя property в поле **Property / port**.
6. Severity: `info`.
7. Оставьте Remediation intent пустым.
8. Заполните rationale и сохраните правило.

Такое правило формирует customization policy и не создаёт violation само по
себе.

### Ограничить opacity набором значений

1. Выберите нужную поверхность.
2. Capability: `appearance.opacity`.
3. Permission: **С условиями**.
4. Constraint: **Допустимые значения**.
5. Значения: `1, 0.64`.
6. Сохраните правило.

### Передать управление layout владельцу композиции

1. Выберите слот или внутренний layout-контейнер.
2. Capability или группа: `Auto layout @1`.
3. Выберите подходящий permission.
4. Control path: `Inherited port`.
5. Введите стабильный id, например `port.body-layout`.
6. Оставьте **Другие пути запрещены** включённым.
7. Сохраните правило.

Editor автоматически создаст component-local control port. Имя внешнего
компонента-владельца здесь указывать не нужно.

## 6. Проверка preview и instance в документе

В нижней панели есть два разных действия.

### Проверить preview

Кнопка **Проверить preview** становится доступна после успешного живого
preview. Она проверяет текущий variant/mode, созданный самим Editor, и нужна для
быстрой проверки того, что правило компилируется и исполняется.

Живой preview по импорту требует Athena evidence с `figma.variants.variantKeys`.
Key Component Set нельзя передавать в `importComponentByKeyAsync`: Figma API
импортирует только конкретный variant component key. Поэтому при импорте одного
`contract.manual.json` Editor не делает ошибочный сетевой запрос и предлагает
проверить выбранный instance. Manual rules при этом загружаются полностью.

### Проверить выделенный instance

Эта проверка предназначена для настоящего экземпляра на странице Figma:

1. Импортируйте `contract.manual.json` либо ZIP с контрактом.
2. Создайте или найдите на странице instance того же компонента.
3. Внесите тестовое изменение, например поменяйте запрещённый padding или
   добавьте stroke.
4. Оставьте выделенным ровно один instance.
5. Нажмите **Проверить выделенный instance**.

Editor не заменяет открытый контракт и не принимает проверяемый instance за
эталон. Он создаёт на временной служебной странице чистый reference instance
того же variant, применяет к нему mode и только разрешённые публичные component
properties, после чего сравнивает фактический instance с этим effective
baseline. Служебная страница и reference instance удаляются в `finally`.

Проверка отклоняется с `Component mismatch`, если ни key варианта выделенного
instance, ни key его родительского Component Set не принадлежат открытому
контракту. Поэтому контракт с identity на `[D] Button` Component Set применим ко
всем его вариантам, даже если у каждого варианта собственный component key.

После проверки центральный preview и Anatomy показывают именно выделенный
instance. Узлы с нарушениями подсвечиваются; нажатие на итоговый chip переводит
фокус на первый узел соответствующей категории, не создавая нового manual
target.

Проверка использует тот же Predicate Engine, что Apollo, и возвращает:

- `compliant` — правило выполнено;
- `violation` — правило нарушено;
- `human-review` — evidence неизвестно или недостаточно;
- `not-applicable` — правило не действует в текущем сценарии.

Нижняя панель показывает только компактную сводку русскими статусами:
**Нарушения**, **Требуют проверки**, **Пройдено**. Нажмите на любую карточку,
чтобы открыть подробную диагностику. Для каждого результата показываются:

- конкретный узел и полный путь в Anatomy;
- capability и severity;
- человеческое объяснение результата;
- rationale исходного manual-правила;
- сравнение **Сейчас → Должно быть** из исходного Apollo trace;
- кнопка **Показать в Anatomy**.

В Anatomy теперь два разных индикатора. Маленькая точка справа относится только
к устойчивости semantic target: зелёная — resolved, жёлтая — ambiguous/unknown,
красная — missing, серая — для слоя ещё нет manual target. Отдельный badge перед
точкой показывает результат Test: красное число — количество нарушений,
жёлтое — проверки, требующие внимания, зелёная галочка — проверки пройдены.

Permission `allowed` остаётся в customization policy и поэтому не создаёт
отдельную строку проверки Predicate Engine.

Во время локального Test правила со статусом `draft` временно получают authority
`active` в тестовой копии compiled contract. Это позволяет проверить правило до
ревью. Канонический manual source и экспортируемый compiled contract не
изменяются и сохраняют статус `draft`. Правила со статусом `deprecated` локально
не активируются.

Если кнопка выключена, значит snapshot ещё не получен. Проверьте componentKey,
доступ Figma-файла к библиотеке и дождитесь окончания preview.

Для проверки выделенного instance кнопка также выключена, если на странице не
выделен ровно один `INSTANCE`.

### Минимальный acceptance-набор для Button

| Изменение instance | Ожидаемый результат |
|---|---|
| Ничего не менять | Нет `violation`. |
| Изменить запрещённый padding | `violation` на соответствующем узле. |
| Добавить stroke при baseline `null` | `violation`; `null` означает, что обводки быть не должно. |
| Изменить label через разрешённое component property | Нет нарушения от этого изменения. |
| Заменить addon через разрешённое instance-swap property | Нет нарушения от этого изменения. |
| Выделить другой компонент | `Component mismatch`, проверка не запускается. |

### Использование того же контура после генерации

Генератор не должен иметь отдельный валидатор. После создания instance он
передаёт factual snapshot в тот же `evaluateCompiledContract` и принимает
результат только при отсутствии блокирующих `violation`/`human-review`.
Customization policy используется до генерации для ограничения допустимых
component properties, а compiled RuleIR — после генерации для проверки
фактического дерева. Сам генератор и автоматический repair в Editor MVP пока не
входят; готовый instance можно проверить кнопкой выше.

## 7. Экспорт

Нажмите **Экспорт ZIP**. Архив содержит:

```text
contract.manual.json
compiled/component-contract.v2.json
coverage.json
validation-report.json
```

### contract.manual.json

Канонический редактируемый источник. Для продолжения работы импортируйте именно
его либо ZIP, в котором он находится.

### compiled/component-contract.v2.json

Детерминированный runtime artifact. Его нельзя использовать как ручной source
of truth.

### coverage.json

Показывает число policy rules, policy-only правил, созданных RuleIR,
неисполняемых правил и покрытие по типам constraints.

### validation-report.json

Содержит ошибки и предупреждения схемы. Экспорт возможен и для draft, но готовым
к Apollo следует считать контракт без validation errors и с reviewed rules.

## 8. Рекомендуемый первый прогон

### Сессия 1 — Button

1. Импортируйте пакет Button.
2. Оставьте desktop Button и один простой variant.
3. Создайте три правила:
   - изменение текста разрешено через host property;
   - ручной radius запрещён;
   - View ограничен известным доменом component property.
4. Проверьте каждый вариант.
5. Экспортируйте ZIP.

Пакет Button содержит много variants. На первом прогоне не пытайтесь описать их
все: задача — подтвердить модель permission/control path/constraint.

### Сессия 2 — CorporateContent

1. Перезапустите Editor и импортируйте пакет CorporateContent.
2. Выберите корень `[D] CorporateContent`.
3. Создайте правила:
   - manual fill запрещён;
   - grid/padding управляется через variable binding;
   - содержимое Body разрешено через slot API;
   - layout Body передаётся через component-local inherited port.
4. Запустите проверку.
5. Экспортируйте отдельный ZIP.

## 9. Ограничения текущего MVP

- Одна component family за сессию.
- При пакете с несколькими контрактами Editor пока автоматически выбирает
  основной desktop-компонент.
- Нет Git publish и синхронизации обратно в Athena.
- Нет AI rule generation.
- Нет редактора произвольного RuleIR.
- Нет page-level и pattern-level правил.
- Нет code mapping editor.
- Нет встроенного генератора и automatic repair; Editor предоставляет тот же
  snapshot + Predicate Engine контур для post-generation проверки.
- Импорт compiled v2 не восстанавливает manual rules.
- Mode preview работает, но mode-scoped conditions пока рекомендуется оставлять
  `all` до отдельной parity-проверки.

## 10. Если что-то не работает

### Пустой preview

- Проверьте наличие `componentKey` в пакете.
- Убедитесь, что текущий Figma-аккаунт имеет доступ к библиотеке компонента.
- Попробуйте выбрать instance в документе и нажать **Взять выделение**.
- Если Figma не ответила за 20 секунд, loader остановится автоматически.
  Authoring по импортированным facts останется доступен; смените variant или
  повторите импорт, чтобы запросить preview снова.

### У TEXT-узла не видно `text.characters`

- Убедитесь, что выбран именно узел с маркером `T`, а не содержащий его frame.
- `text.characters` теперь показывается первым в Observed facts.
- После обновления сборки полностью перезапустите development-плагин в Figma:
  открытое окно не подменяет уже загруженный `dist/code.js` автоматически.

### Пустая Anatomy

В импортированном пакете может отсутствовать structure signature. Живой preview
заполнит дерево фактической структурой instance.

### Validation error после сохранения

Проверьте target, capability, constraint values, rationale для reviewed-правила
и существование inherited port.

### Target стал ambiguous или missing

Athena regeneration либо другой variant изменил структуру. Не создавайте новое
правило автоматически: сначала выберите корректный слой и подтвердите semantic
target вручную.
