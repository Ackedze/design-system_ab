# Подготовка и проверка контрактов компонентов

## Разрешённый публичный swap: привязка и внешний asset

Подтверждённый общий механизм в core 0.1.17 / Editor 0.2.103 использует explicit
`declaredTargetConfigurationVersion=2` с identity v3. Его применяют только когда
собственная норма компонента явно разрешает безусловный внешний swap через
точный root-owned `slot-api` control path с `contentOwnership=external` и
`exclusive=true`. Сам факт наличия INSTANCE_SWAP не вводит разрешение.

Для каждой исходной native variant reference configuration pin вычисляется
`publicSwapDeclaredTargetReferenceHash(reference, {targets, policies, representations})`;
`policies` — manual rules при авторинге. Exact и portable reference pins остаются
провенансом. Runtime отдельно доказывает source occurrence, nearest owner,
typed mainComponent port и единственную привязку в независимом reference.
Выбранный asset/его descendants не определяют identity слота; ограничения
самого слота и host продолжают действовать. Нельзя снять весь pin, считать имя
доказательством, нормализовать недекларированный порт или наследовать target
identity потомкам другого asset. У старой v1 схемы семантика не меняется.

Проверку общего механизма переиспользуем с точными pins, но новый native port
и условия компонента проверяем отдельно: разрешённый swap, собственное
нарушение размера/оформления, RESET и insufficient proof. Доказательство:
`Link/reports/reading-fixes/public-instance-swap-2026-10-11/HANDOFF.json` — local
synthetic и retained-native replay; fresh installed r4 и independent review
ещё не выполнены. Лимиты Link не переносятся в другие компоненты.

Версия 0.1 от 10.10.2026. Общая инструкция для ручной и автоматической подготовки контрактов в `current-contract-packages`. Она собирает повторяемые способы работы; значения, исключения и статус каждого компонента задаёт его собственный manual. Исследование полного накопленного опыта продолжается в «Apollo CB :: System Analysis».

## Начало работы

Текущие manual и необходимые факты находятся в основных папках компонентов `design-system_ab/JSONS/web/components/...`; их точные пути, revision и SHA задаёт [индекс исходников](../../JSONS/indexes/component-contracts.index.json). ZIP из [manifest.json](manifest.json) — производный установочный пакет. Для изменений редактируй canonical manual и факты, затем пересобирай и согласуй ZIP/индексы по [AGENTS.md](AGENTS.md). Старые authoring-папки и compiled projection сохраняются как историческое происхождение. Закреплённая родителем прежняя версия хранится отдельно в `contract-versions/rN` и не подменяется текущей.

Переиспользуй способ проверки и структуру шаблона. Домены, размеры, лимиты, component keys, привязки D/M и исключения получай из источников нового компонента. Например, наличие лимита текста у BenefitCard не вводит такой же лимит у другой карточки или у всех Link.

Для ограничения на вложенную native-цель сверь применимость со всеми опубликованными вариантами, где цель действительно связана. Если в части вариантов цели нет, проверь один такой вариант: неактивное ограничение не должно блокировать остальные локальные проверки. Применимость доказывается source/reference и типизированным VARIANT, а не одним редактируемым значением; отсутствие привязки само по себе не доказывает отсутствие цели. Проверенный пример — [IconView r11](IconView/reports/size24-eligibility-r11-2026-10-20/EVAL.json). Это одна активная/неактивная ветка механизма, а не новая ручная матрица размеров.

## Классификация исходных требований

До заполнения формы составь таблицу исходных требований. Для каждого требования укажи источник, RuleID, смысл, владельца, область и маршрут проверки.

| Что описывает требование | Куда его направить |
| --- | --- |
| Состав, доступные свойства, геометрию, внешний вид или текст компонента | В компонентный контракт; выбрать существующий типизированный способ проверки |
| Собственные ограничения вложенного компонента | В отдельный зависимый контракт; у родителя сохранить требования к использованию ребёнка |
| Выбор компонента, порядок действий или сборку композиции в контексте | В контекстное правило, паттерн или рецепт с явными входными данными |
| Интерактивность, которую статичный снимок Figma не доказывает | В маршрут проверки кода, поведения или последовательности состояний |
| Рекомендацию либо описание параметра | В документацию или metadata; не создавать нарушение без нормы |
| Неоднозначную формулировку или неподдержанный способ проверки | Сохранить unresolved и конкретный вопрос; не считать заполненный текст исполняемым правилом |

Контекстные нормы не теряются при выделении из Figma scope. Разрешение публичного API, запрет instance swap и ограничения внутреннего устройства — разные решения. Подтверждённое решение владельца имеет приоритет над прежним примером.

## Повторяемые условия корректного заполнения

- Выбирай semantic target и scope до constraint. Корень, все потомки и потомки без корня имеют разный смысл. Область доказанной зависимости учитывается отдельно.
- Получай привязки каждого применимого варианта и представления из native фактов. Совпадение имени, позиции или номера слоя не доказывает identity; привязки desktop не переносятся на mobile автоматически.
- Перед передачей нового native capture сравни reference pin с независимым снимком установленного Editor. Сортировка путей с разным регистром может различаться между capture host и runtime: canonical projection строй в runtime shared core, сохраняя raw capture. `reference-pin-stale` означает неполноту проверки, даже когда violations=0. Не отключай identity guard и не перепривязывай пакет к текущим overrides; сравни точное содержимое независимых references. Пример и регрессия: `Link/authoring/reports/editor-report-replay.r2.json`.
- Native default PASS не доказывает поддержку публичной конфигурации. Проверяй разрешённые TEXT/BOOLEAN вместе с negative и RESET, включая resolved targets и inconclusive. В core 0.1.15 / Editor 0.2.99 явный `declaredTargetConfigurationVersion=1` и `configurationReferenceHash` отделяют typed declared root TEXT/BOOLEAN values от identity; вычисляй pin общим core, сохраняй остальные exact source/owner/topology guards. Это не разрешение на произвольную правку и не поддержка nested VARIANT/INSTANCE_SWAP: такие поля остаются pinned и требуют отдельной проверки. Старые policies без opt-in не переписывай. Evidence: `Link/reports/skill-evals/link-r3-root-configuration-2026-10-10/eval.json`; installed r3 ещё pending.
- Используй независимый эталон. Проверяемый экземпляр, его текущие overrides и подпись тесткейса не задают ожидаемую норму.
- Сохраняй native тип и регистр значений. BOOLEAN `true` и VARIANT `True` не взаимозаменяемы. При известном API используй выбор значений, включая множественный выбор, а не ручную строку.
- Различай видимость и состав: скрытие может быть допустимо, хотя удаление или подмена того же элемента запрещены. UNKNOWN identity не превращается в разрешение изменения.
- Разрешение менять содержимое или Type ребёнка не разрешает менять всю его внутреннюю структуру. Для разрешённой настройки нужен корректный независимый baseline выбранного состояния.
- Applicability определяет, когда действует правило. Дополнительные условия отдельного baseline-сравнения не выключают остальные сравнения группы.
- Отсутствие доказательств даёт неполноту проверки; доказанная неприменимость даёт `notApplicable`. Не ослабляй норму ради зелёного отчёта при расхождении с библиотекой.

## Подготовка нового контракта

1. Сверь актуальные исходные нормы, паспорт, native API, варианты и зависимости. Отдели решения владельца от наблюдений библиотеки.
2. Для каждой нормы выбери способ из каталога. Подготовь черновик полей пакетно; автор подтверждает смысл, исключения и нормативные значения.
3. Скомпилируй черновик. Сопоставь каждую исходную норму с её проверками, policy либо отдельным маршрутом. Найденный пробел исполнения запиши с причиной и способом устранения.
4. Из выбранных способов подготовь тестовую матрицу с явными параметрами и ожидаемыми RuleID. Сначала используй готовые семейства тестов, затем добавляй особенности компонента.
5. Проверь подготовку, живое чтение и результат в заявленной области. Сохрани evidence; затем согласуй пакет и manifest. `Reviewed` и `Ready` назначай по фактически закрытой области.

Изменения нормативных требований требуют синхронизации с `Правила`, `Леджер` и Predicate по родительскому AGENTS.md. Обновление этой инструкции не изменяет нормы компонентов.

Перед Google `updateCells` проверяй фактическую форму входа и каждый индекс через `Number.isSafeInteger`: `undefined`, `NaN`, `null` и строки недопустимы. Обе границы каждой оси обязательны, размеры rectangle должны точно совпадать с `rows/values`, а диапазон — помещаться в прочитанную grid metadata. Сохраняй исходные CellData всего записываемого диапазона и сверяй readback. Отсутствующая строковая граница может превратить изменение одной строки в очистку колонки. Подтверждённый случай и восстановление: `Link/reports/ledger-range-recovery.r2.json`.

## Матрица тестов

Для каждой исполняемой нормы сохраняй связь «исходное правило → compiled checks → кейсы». Один source RuleID может создавать несколько проверок; один кейс может затронуть несколько норм.

| Поле кейса | Что указать |
| --- | --- |
| Основание | Source RuleID, целевые compiled RuleID и конкретный способ проверки |
| Условия | Representation/platform, variant, modes, публичные properties и необходимые context inputs |
| Подготовка | Исходный экземпляр и одна целевая мутация либо явный переход состояния |
| Ожидание | Результат конкретной проверки и причина; возможные дополнительные результаты учитывать отдельно |
| Восстановление | Действие RESET и ожидаемое исчезновение целевого нарушения |
| Доказательство | Версия пакета/Editor/core, отчёт, SHA и фактическая область приёмки |

Базовый цикл — положительный контроль, отрицательная мутация, RESET. Для доменов и числовых лимитов добавь границы; для условных норм — активное и неактивное условие; для чувствительных к доказательству норм — недостаточные данные. Не ожидай фиксированное общее число ошибок вместо проверки нужных RuleID.

Разделяй проверку общего оператора, привязок нового компонента и его нормативных исключений. Уже принятые результаты сохраняй со scope и pins; повтор нужен при затронувшем их изменении или открытом гейте. Сокращение числа ручных запусков не отменяет установленную полноту вариантов, live или release приёмку.

Не повторяй полную ручную матрицу общего текстового механизма для каждого компонента. Сошлись на принятый regression/evidence общего core, автоматически сверь actual constraint/IR и параметры нового контракта, затем проверь новую native привязку и отличающиеся лимиты, условия или маршрут управления. Когда эти привязки уже подтверждены положительным, отрицательным и RESET прогоном, не добавляй ещё один live кейс только с другим разрешённым текстом. Для Link r3 такая область подтверждена [configured Label / preserving RESET](Link/reports/live-review-r3-2026-10-11T06-07-06Z/review.json); дополнительный ввод 38 символов снят как необязательный повтор. Это не native PASS невыполненного кейса и не перенос лимитов BenefitCard в Link. [Решение и evidence](Link/reports/text-evidence-reuse-2026-10-11/decision.json).

Производные значения в review metadata, включая число символов, вычисляй из фактического raw input тем же способом, что и проверяемый механизм; не вводи их вручную. Перед seal сравни сводные значения с результатами по каждому capture. Для Unicode textContentV1 использует code points; число UTF-16 code units не заменяет эту метрику. Исправление metadata закрытого receipt оформляй отдельным correction receipt, сохраняя исходные bytes и seal.

## Передача ручных проверок пользователю

Формат согласован владельцем 10.10.2026. Передавай небольшой последовательный блок кейсов таблицей **прямо в ответе**, чтобы пользователь мог открыть конкретный проверяемый экземпляр компонента, выставить параметры и сразу сопоставить результат. Ссылка на сохранённую полную матрицу дополняет эту таблицу.

Перед таблицей укажи пакет/revision, режим проверки и общие условия: representation/platform, variant, публичные properties, modes и context inputs, если они нужны. Значения бери из данного компонента; BOOLEAN и строковый VARIANT записывай с точным native типом и регистром. Ссылка должна выбирать сам проверяемый компонент.

| Компонент | Параметры | Ожидаем |
| --- | --- | --- |
| Кликабельное название кейса → прямая Figma-ссылка на проверяемый экземпляр компонента | Точные значения и место изменения; отметь, если мутация уже подготовлена | Результат целевой проверки и конкретный compiled RuleID |
| Кликабельное название того же кейса — RESET → тот же экземпляр | Какие исходные значения восстановить на том же экземпляре | Целевое нарушение исчезает; ожидаемый результат остальных проверок укажи по подтверждённой области |

Используй проверенный `fileKey` и `node-id` самого проверяемого узла компонента, обычно `INSTANCE`. Основная ссылка не должна вести на фрейм-обёртку, страницу или секцию. RESET относится к тому же экземпляру; отдельный чистый контроль не заменяет восстановление отрицательного кейса. После каждого прогона, включая RESET, проси отдельный отчёт. Для ожидаемого нарушения указывай его свойство и RuleID; длинные IDs можно вынести сразу под таблицу. UNKNOWN или дополнительные диагностики сохраняются для разбора, а не подгоняются под ожидаемое общее число ошибок.

Если fixture ещё не подготовлен либо проверка требует отсутствующих входов, явно отметь это в строке и не включай кейс в текущий блок запуска. Полная матрица и receipts остаются в рабочей папке компонента. Этот формат меняет способ передачи проверки, а не нормы, scope или статус приёмки контракта.

## Как пополнять инструкцию

Новый повторяемый случай добавляй в существующий способ либо заводи новый, если отличается механизм: формулировка, поля, условия, исключения, тесты и ссылка на evidence. Специфичные значения остаются в контракте компонента.

Дефект Editor фиксируй отдельно от нормы и шаблона. Влияющие на чтение контрактов изменения переноси в бэклог Apollo v4. Исправление общего дефекта закрепляй регрессионной проверкой; возвращение тестового экземпляра в исходное состояние не доказывает исправление дефекта.

Ближайшее развитие: проверить каталог на всём накопленном наборе, определить полезные пресеты и генерацию тестов, затем выделить краткий `SKILL.md`, который направляет агента к этой инструкции и актуальным схемам без дублирования содержания.
