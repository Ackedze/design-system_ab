# План единой генерации фронта и Figma по промпту

Зафиксирован 5 октября 2026 года по запросу владельца. Документ задаёт план будущей реализации: один промпт превращается в общую спецификацию экрана и общий план композиции, из которых создаются Figma-макет и фронт. Решения о компонентах, содержимом, состояниях и поведении принимаются в общем контуре; особенности каждой среды обрабатывают её адаптеры.

Исходная подборка контрактов: `design-system_ab/experiments/current-contract-packages`. На дату фиксации проверено содержимое ZIP. План не меняет компонентные нормы, статусы приёмки, паттерны или production-публикацию. Описанные ниже сервисы, форматы и этапы являются предлагаемой архитектурой; наличие этого документа не означает, что они уже реализованы.

## Основное решение

Общий маршрут:

```text
Промпт и контекст задачи
        ↓
Спецификация экрана
        ↓
Выбор контрактов, паттернов и закреплённых зависимостей
        ↓
Общее семантическое дерево и план композиции
        ↓
Проверка плана и доступности представлений
        ↓
Адаптер Figma                 Адаптер фронта
        ↓                           ↓
Библиотечные экземпляры       Компоненты приложения
        ↓                           ↓
Получение фактов и проверка результата в каждой среде
        ↓
Сопоставление с общей спецификацией, исправления и отчёт
```

Оба адаптера получают одну версию плана. Они не интерпретируют исходный промпт повторно и не принимают независимо решения о смысле интерфейса. Один компонент может иметь разную структуру в Figma и коде; соответствие определяется семантикой и проверенным отображением API, а не совпадением числа слоёв и DOM-узлов.

Генерация только Figma или только фронта использует тот же маршрут до выбора исполнителя. Отсутствие подтверждённого кодового представления не препятствует работе доступного Figma-представления; для запрошенного фронта это фиксируется как ограничение конкретного результата.

## Входные данные

| Вход | Что необходимо знать |
| --- | --- |
| Назначение | Пользовательская задача, сценарий и результат действия |
| Поверхность | Страница, модальное окно, секция или другой контейнер |
| Среда | Desktop, mobile-web, требуемые размеры и адаптивные состояния |
| Содержимое | Заголовки, подписи, значения, валюты, пояснения и действия |
| Состояния | Начальное, loading, empty, error, success и другие нужные состояния |
| Поведение | Переходы, события, валидация, источники данных и результаты действий |
| Условия композиции | Иерархия, ограничения ширины, переносы, сетка и выбранные паттерны |
| Результат | Figma, фронт или оба; целевой файл и контейнер Figma, проект фронта |

Известные значения извлекаются из промпта и подтверждённого контекста. Существенные неопределённости уточняются, остальные предположения записываются в спецификацию. Наличие кнопки «Отправить» само по себе не задаёт endpoint, права доступа или успешный ответ сервера. Для демонстрации допустима явно обозначенная модель поведения без заявления об интеграции с реальным сервисом.

## Источники и их ответственность

| Источник | Ответственность |
| --- | --- |
| Промпт и спецификация | Смысл экрана, пользовательские данные и независимые ожидания |
| `contract.manual.json` из выбранного ZIP | Авторские нормы, семантический API, представления, профили и инструкции генерации |
| Athena facts внутри пакета | Подтверждённые ключи, свойства, варианты, структура и библиотечные эталоны |
| Compiled контракт | Исполнение поддержанных проверок и диагностика |
| Закреплённые зависимости | Контракты вложенных компонентов с указанными revision и hashes |
| Подключённые паттерны | Выбор и применение компонентов, композиция, интервалы и адаптация |
| Редакционные правила | Текст и форматирование данных |
| Проверенное отображение API фронта | Импорты, props, children, events и способы реализации общей семантики |

Manual остаётся редактируемым источником компонентных норм. Проекции для генератора, compiled и индексы являются производными. При загрузке проверяются соответствие manual, facts и compiled, происхождение и hashes. Противоречащие версии не объединяются молча.

README и manifest используются как навигация и сведения о приёмке. На дату фиксации они отстают от части ZIP: desktop CorporateContent указан в manifest как r11, фактический manual в архиве — r12; ButtonsGroup r52 отсутствует в manifest. Приёмка обновлённого пакета не выводится только из текста старого manifest или поля `ready`.

## Общая спецификация и план композиции

Предлагаются два производных документа. Их схемы предстоит разработать и версионировать.

**Спецификация экрана** описывает намерение до привязки к библиотечным представлениям: сущности, роли блоков, содержимое, действия, состояния и поведение на разных ширинах. В ней сохраняются независимые ожидания, необходимые для проверки: например, растягивание кнопки, ограниченная ширина контейнера и поведение текста.

**План композиции** связывает спецификацию с контрактами. Для каждого узла он хранит:

- стабильный идентификатор и семантическую роль;
- выбранный `componentId`, revision и hashes пакета;
- семантические свойства и типизированные данные;
- содержимое именованных слотов и связи с дочерними узлами;
- layout intent и ссылки на определяющие его паттерны;
- состояния, события и переходы;
- выбранные представления для целевых сред;
- происхождение решения: запрос, профиль, компонентная норма или паттерн;
- предположения, незакрытые ограничения и ожидаемые проверки.

В общем дереве записывается роль содержимого, например `body`, а имя Figma-свойства или React API выводится адаптером. Значения суммы и валюты сохраняются как данные с явной семантикой. Преобразование Figma-строк в числовой API фронта выполняется только по подтверждённому bridge; произвольный Custom-текст нельзя автоматически трактовать как число.

Профиль генерации задаёт стартовые настройки компонента. Отсутствие профиля означает отсутствие готового рецепта; оно не доказывает запрет использования компонента. Дальнейшие настройки выводятся из разрешённого API, задачи и паттерна, с проверкой полученного плана.

## Последовательность генерации

1. **Разобрать запрос.** Сформировать спецификацию, определить нужные результаты и состояния, записать предположения.
2. **Загрузить пакеты.** Прочитать ZIP из указанной подборки, проверить целостность, разрешить закреплённые зависимости и возможности каждой среды.
3. **Выбрать композицию.** Подключить необходимые паттерны и редакционные правила. Сначала определить роли, затем семейства компонентов.
4. **Разрешить представления.** Выбрать platform, surface и `representationId`, определить опубликованные ключи или импорты и применимые API bindings.
5. **Построить общий план.** Применить подходящие профили, задать содержимое, слоты, состояния, layout intent и поведение.
6. **Проверить план до выполнения.** Сверить домены свойств, зависимости, границы владения, поддержку представлений и наличие требуемых входных данных. Проверки, которым нужны фактические узлы и reference, остаются на этапе после выполнения.
7. **Выполнить адаптеры.** Создать Figma и фронт из одной закреплённой версии плана. Сохранить связь каждого узла плана с созданными экземплярами и кодом.
8. **Получить факты и проверить.** Выполнить проверки компонентов, вложенных зависимостей, композиции, поведения и общего смысла результата.
9. **Исправить и повторить затронутые проверки.** Изменение общего решения вносится в план и распространяется на оба результата; локальная ошибка преобразования исправляется в соответствующем адаптере.
10. **Сохранить результат.** Выдать артефакты, версии входов, результаты проверок и остающиеся ограничения.

## Адаптер Figma

Адаптер создаёт опубликованные библиотечные instances по ключам выбранных представлений. Семантические настройки переводятся через bindings, transformations и объявленные control paths. Поддержка каждого вида операции подтверждается на реальном API; наличие binding в JSON само по себе не доказывает, что исполнитель умеет его применить.

Содержимое desktop CorporateContent передаётся через native SLOT `[D] Body#135096:3`, mobile-web — через `[M] Body#135096:2`. Пустой `body` сохраняет пустой слот. Профиль empty не требует оставлять все макеты пустыми, а библиотечный placeholder не выдаётся за содержимое задачи.

Оболочка сохраняет защищённый effective baseline текущего варианта и режима. Высота корня CorporateContent не ограничивается вымышленным запретом: `layout.sizingVertical` отсутствует в принятом locked selection этих пакетов. Выбор разрешённого page background mode задаётся задачей или паттерном.

Слоты, заменяемые компоненты и управляемые свойства обрабатываются по контракту. Исполнитель не подменяет доступный библиотечный элемент произвольной ручной копией. Структура пользовательского содержимого формируется в разрешённых слотах; её оформление и layout получают отдельное основание.

В отчёт попадают созданные и изменённые node IDs, component keys, свойства, variable modes и сопоставление с узлами общего плана. Reference получается независимо от проверяемого экземпляра с учётом текущих variants и modes.

## Адаптер фронта

Адаптер переводит то же дерево в существующие компоненты целевого проекта. Для каждого компонента требуются подтверждённые package/import, code representation и mapping семантических свойств, слотов и событий.

Figma variant names, Body SLOT IDs и variable modes не превращаются автоматически в React props. Несуществующие props не создаются для имитации совпадения API. Figma-only пресет AmountStyles может реализовываться композицией доступных фронтовых компонентов и стилей после проверки bridge; наличие пресета не означает наличие одноимённого React-компонента.

Фронт реализует описанные состояния, адаптацию, события и доступность. Подключение backend выполняется по входной спецификации и проверенному API. Данные демонстрации и реальная интеграция обозначаются отдельно.

Для проверки собираются необходимые факты из исходников, DOM, computed styles и поведения. Их набор и операторы расширяются явно. Figma-specific предикаты не запускаются на DOM без подтверждённого преобразования. Общие требования проверяются в обеих средах, а требования, относящиеся только к одной среде, сохраняют эту область действия.

## Зависимости и границы владения

Текущие связи:

```text
ButtonsGroup r52 → Button r31 → Spinner r8
AmountStyles r10 → Amount r5
CorporateContent → внешнее содержимое Body из плана задачи
```

Дочерние правила выполняются из закреплённого контракта и не копируются в родительский. Родитель задаёт ограничения композиции и может владеть определёнными свойствами вложенного компонента; библиотечный reference должен учитывать это владение. Standalone default дочернего компонента не заменяет родительскую конфигурацию.

Наличие Spinner не доказывает loading родителя. Для Button сохраняются объявленное состояние и фактическая конфигурация Addon; размер и палитра согласуются с контрактом Button и проверяются вместе с собственными нормами Spinner.

Содержимое Body принадлежит вызывающей композиции. Успешная проверка CorporateContent не означает успешную проверку каждого компонента внутри Body. Замещённый Addon также проверяется в своей роли; его содержимое не сравнивается с библиотечным placeholder как с обязательной структурой.

## Проверка и исправления

Проверки разделяются по тому, какие факты им нужны:

| Проверка | Основание |
| --- | --- |
| План | Домены API, доступность представлений, зависимости и независимые ожидания |
| Компонент | Его текущий контракт, фактическое состояние и независимый reference |
| Композиция | Подключённые паттерны, границы слотов и спецификация |
| Фронтовое поведение | События, доступность, переходы состояний и контракт данных |
| Соответствие двух результатов | Одинаковые смысл, данные, действия, состояния и адаптивные решения |

Соответствие Figma и фронта не сводится к обязательной пиксельной идентичности. Допустимые визуальные отличия должны иметь основание в представлениях и адаптерах. Там, где задано точное визуальное ожидание, оно проверяется отдельно для соответствующего viewport и состояния.

Результат проверки сохраняет RuleID, владельца, область действия, факты и причину. Нарушение, успешная проверка, неприменимость, разрешение policy-only и неполная проверка остаются различимыми. Missing или ambiguous facts не превращаются ни в успех, ни в доказанное нарушение.

Для переходного требования Button loading-preserves-width фиксируется пара состояний одного экземпляра при одинаковых внешних условиях. Ожидания block, nowrap, textResizing и constrainedWidth берутся из спецификации, а не выводятся из actual, который проверяется.

Автоматическое исправление выполняется только поддержанной операцией в пределах разрешённого API. Если исправление требует изменения нормы, нового представления или разрешения конфликта источников, генератор выдаёт диагностированное ограничение; контракт не переписывается ради зелёного результата.

## Этапы реализации

| Этап | Результат | Критерий завершения |
| --- | --- | --- |
| 1 Учёт пакетов | Загрузчик ZIP и воспроизводимый снимок версий | Реальные manual revisions, hashes, зависимости и наличие compiled определяются из пакетов; расхождения manifest диагностируются |
| 2 Общая модель | Версионируемые схемы спецификации и плана | Семантика, слоты, состояния, поведение и происхождение решений описываются без привязки к одной среде |
| 3 Проекция генерации | Производный интерфейс к manual и facts | Доступны semantic API, representations, profiles, instructions и ограничения; второй редактируемый источник норм не появляется |
| 4 Планировщик | Преобразование промпта в проверяемый план | Выбор компонентов и паттернов объясним, зависимости закреплены, неопределённости явно сохранены |
| 5 Исполнитель Figma | Создание и чтение результата | Профили, свойства, native SLOT и вложенные зависимости работают; фактические узлы сопоставляются с планом |
| 6 Исполнитель фронта | Проверенные mappings и генерация приложения | Используются реальные imports и props; состояния, адаптация и поведение реализуются по той же спецификации |
| 7 Проверяющий контур | Общий формат диагностик и сбор фактов каждой среды | Нужные проверки выполняются без вымышленных фактов; сохраняются границы приёмки и неизвестные результаты |
| 8 Сквозная приёмка | Один сценарий в обеих средах | Figma и фронт получены из одной версии плана; позитивные и негативные случаи проверены, воспроизводимость доказана |

Этапы отражают зависимости работ; реализацию общих моделей, mappings и сборщиков фактов можно вести совместно после фиксации их интерфейсов. Разработка самого генератора является следующей задачей после принятия этого плана.

## Первый сквозной сценарий

Предлагаемый пилот: экран с итоговой суммой, действием подтверждения и состоянием загрузки, в desktop и mobile-web представлениях. Он проверяет CorporateContent Body, AmountStyles с Core Amount, Button со Spinner, типизированные данные суммы и соответствие состояний между Figma и фронтом.

ButtonsGroup включается в desktop-ветку там, где нужна группа действий. В текущей подборке его ручной пакет описывает desktop; поддержку mobile-web нельзя выводить из наличия desktop-пакета. Обвязка страницы и другие компоненты подключаются только после определения их источников и mappings. На первом этапе можно проверять содержимое CorporateContent без заявления о полной готовности всех частей продуктовой страницы.

Проверить минимум: штатную сборку, смену данных, допустимую настройку свойств, запрещённый визуальный override, неверную зависимость, отсутствующие факты и переход в loading. Ожидаемые результаты задаются до исполнения. Ошибка одного адаптера не должна скрываться успешной проверкой другого.

## Текущие ограничения и необходимые решения

- В подборке отсутствует Modal. Его актуальный пакет и mappings нужны для включения модальных сценариев.
- ButtonsGroup r52 не содержит `generation.profiles`, `generation.instructions` и semantic API; требуется определить производный рецепт использования или дополнить авторский контракт штатным маршрутом.
- Code representations Button, Amount и Spinner имеют статус draft. У AmountStyles, ButtonsGroup и CorporateContent кодовые представления в проверенных manual отсутствуют. Их mappings и границы поддержки фронта предстоит подтвердить.
- Host compiled отсутствует в ZIP Button, Spinner, Amount и AmountStyles; там, где нужна пересборка, используется общий compiler core с facts и закреплёнными зависимостями. В ZIP AmountStyles и Button лежат compiled дочерних контрактов. Для runtime не следует предполагать, что каждый ZIP уже содержит compiled собственного host.
- Паттерны композиции и редакционные источники не выбираются автоматически из одного набора компонентных ZIP. Их реестр, версии и способ подключения входят в отдельную часть загрузчика.
- Компиляция проверок и статус Figma readiness не являются подтверждением готовности генерации фронта. Готовность следует учитывать отдельно для Figma generation, Figma validation, code generation, code validation и межсредового соответствия.
- Устаревшие README и manifest нужно согласовать с фактическими экспортами отдельной задачей. Этот план не меняет пакеты и не переобъявляет их приёмку.

## Результат каждого запуска

Сохраняются исходный запрос и его контекст, спецификация, общий план, снимок версий источников, артефакты обоих адаптеров, связь узлов плана с результатом и отчёт проверок. Отчёт показывает, что исполнено, что проверено, где обнаружены нарушения и что осталось неизвестным.

Критерий готовности единого генератора: один закреплённый план позволяет воспроизвести оба результата с одинаковым смыслом и заданным поведением; каждый результат проходит применимые проверки в своей среде, а непокрытые области явно указаны. Обновление контракта, паттерна или адаптера меняет версию входов и вызывает повторную проверку затронутого сценария.
